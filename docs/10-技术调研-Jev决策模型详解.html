Jev 详解

TypeSafe AI 的首个「System One 模型」——一个不生成文本、只输出类型化概率决策的新型 AI，以及它与「拾光」的适配性分析
厂商：TypeSafe AI 发布：2026-09-15 模型：jev-latest 调研日期：2026-09-19 拾光技术调研 · 10
TL;DR

Jev 是 2026 年 9 月中旬在硅谷爆火的新模型：它主动砍掉文本生成能力，专做「输入一段状态文本 → 对一组预定义问题返回带校准概率的类型化答案」。分类、路由、信息抽取等闭集判断任务上，官方宣称比同类 LLM 快 200 倍、便宜 400 倍。它与本项目「一句话五域抽取」中约六成的字段（活动分类、情绪、财务判定等）范式高度契合，且已实测腾讯云服务器可直连其 API；但中文能力未经验证、上线仅数日、无法生成文本和抽取开放词汇（如人名）——当前结论：不接入，列入观察清单，保留 42 句 PoC 测试集作为未来试点基准。

一、Jev 是什么

2026 年 9 月 15 日前后，一个名叫 Jev 的模型在硅谷 AI 开发者社区刷屏。它由 TypeSafe AI 公司发布，是该公司首个公开的「System One 模型」。

它颠覆的地方在于：它不会写代码、不会写文章、甚至不会聊天。Jev 主动砍掉了过去几年大模型赖以展现「智能」的语言生成能力，回答问题时输出的不是一段文字，而是类型安全的结构化答案 + 校准概率。36 氪的报道称之为「一个不说话的 AI」。

它提出的核心质疑是：AI 的"智能"是否一定要通过高资源消耗的自回归文本生成来完成？分类、判断、路由这类高频决策任务，有没有更快、更省、更靠谱的方式？

名字里的「System One」借用自心理学家丹尼尔·卡尼曼《思考，快与慢》中的双系统理论：System 1 = 快思考（直觉、毫秒级、低能耗），System 2 = 慢思考（推理、生成、高能耗）。传统 LLM 是 System 2，Jev 想做 AI 系统里的 System 1。

二、核心范式：与 LLM 的本质区别

维度传统 LLM（GPT / GLM / Claude…）Jev（System One）
输出形态自回归逐 token 生成文本类型化答案（选项/分数/概率），无文本
接口范式Prompt → 补全State（状态）+ Questions（问题组）→ Answers
多问题串行生成，问题越多越慢并行评估，加问题几乎不增加延迟
置信度让模型"自报"（常不可靠）原生校准概率（每个答案带概率分布）
幻觉风险存在（编造事实/格式漂移）闭集输出，结构上不会"编"出选项外内容
速度秒级～十秒级官方宣称最快 200×（毫秒级决策）
开放推理/生成✅ 擅长❌ 完全不能（title、摘要、追问都做不了）
定位通用大脑Agent 环路中的快速决策件（路由/分类/拦截）

一句话：Jev 不是 LLM 的替代品，而是和 LLM 搭配的「快反射」——LLM 负责理解、推理和生成，Jev 负责过程中成千上万次高频结构化判断。

三、接口详解

3.1 端点与认证

  • 端点：POST https://api.typesafe.ai/v1/systemone
  • 认证：Authorization: Bearer <API_KEY>（密钥在 console.typesafe.ai/keys 申请）
  • 请求体三个顶层字段：state（待分析文本）、model（如 jev-latest）、questions（问题字典，键为自定义名）

3.2 三种问题原语（Primitives）

CHOICE
选择题

从一组选项中挑选。criteria 为「选项名 → 描述」字典。

例：工单属于哪个部门？活动属于八大分类中的哪类？

→ choice + confidence + probabilities
SCORE
评分题

按有序等级量表打分。criteria 为有序描述数组（0 起编号）。

例：用户沮丧程度（平静/不满/愤怒）？情绪强度多高？

→ score + confidence + legend + probabilities
NOUL
是非题

判断一句陈述为真的概率，无需 criteria。

例：这句话提到金额了吗？这个工单紧急吗？

→ noul（0～1 概率）

3.3 完整请求示例（REST）

一次性对同一 state 混合提出三种问题（并行评估）
curl -X POST https://api.typesafe.ai/v1/systemone \
  -H "Authorization: Bearer $TYPESAFE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "jev-latest",
    "state": "用户刚发来的消息：部署又失败了两次，客户已经在看到 500 报错了！",
    "questions": {
      "department": {
        "type": "choice",
        "instructions": "这条工单应该路由到哪个部门？",
        "criteria": { "technical": "技术故障与部署问题", "sales": "销售咨询", "billing": "账单问题" }
      },
      "frustration": {
        "type": "score",
        "instructions": "评估发信人的沮丧程度",
        "criteria": ["平静专业", "明显不满", "愤怒失控"]
      },
      "is_urgent": {
        "type": "noul",
        "instructions": "这条消息表达了紧急性或时间敏感"
      }
    }
  }'
响应（含每个答案的校准概率分布 + token 用量）
{
  "model": "jev-1.13.0",
  "answers": {
    "department": {
      "type": "choice",
      "choice": "technical",
      "confidence": 0.78,
      "probabilities": { "technical": 0.85, "sales": 0.0, "billing": 0.15 }
    },
    "frustration": {
      "type": "score",
      "score": 1.0,
      "confidence": 1.0,
      "legend": { "0": "平静专业", "1": "明显不满", "2": "愤怒失控" },
      "probabilities": { "0": 0.0, "1": 1.0, "2": 0.0 }
    },
    "is_urgent": { "type": "noul", "noul": 1.0 }
  },
  "usage": { "input_tokens": 392, "output_tokens": 65 }
}
官方最佳实践：把复合问题拆成原子问题，在代码里组合结果（例如不要问"这是紧急的技术工单吗"，而是拆成"紧急吗"+"是技术工单吗"两个问题并行问）。这与本项目「五域独立判定」的抽取设计思路天然一致。

  • 官方内部评估单次判断成本约 $0.0004；部分聚合渠道（如 AI ML API）略贵（~$0.058/M）。
  • 并行评估是核心省时机制：一次请求问 3 个问题和问 1 个问题延迟几乎相同，只增加少量 token。
  • TypeSafe 后续 System One 系列模型定价区间 $0.20～$10/MTok，Jev 是其中最便宜的入门款。

注：以上为厂商官方与早期社区口径（2026-09），"200×/400×" 为特定基准下的宣称值，尚未有中立的第三方大规模复测。

五、典型应用场景

  • 模型路由：Agent 每步先让 Jev 判断任务复杂度，简单查询走便宜模型、高风险推理走旗舰模型（LangChain ModelRouterMiddleware 的标准用法）。
  • 邮件/工单分诊：部门路由（Choice）+ 优先级（Score）+ 紧急度（Noul），一次调用并行出全部结果。
  • 工具调用风险拦截：Agent 执行危险工具（删库、转账、发邮件）前，Jev 毫秒级判断风险并拦截。
  • 内容分类与审核：垃圾短信判定、内容分级等高频闭集分类。
  • 浏览器自动化：开源项目 jev-browser——LLM 负责规划，Jev 负责页面上每一步的快速决策。
  • 发票/单据处理：并行判断单据类型、异常风险、审批级别等多个独立维度。

六、局限与风险（本调研的审慎结论依据）

问题等级说明

七、与「拾光」的适配分析

本项目的高频 AI 工作负载是一句话五域抽取（时间/待办/财务/心情/饮食）。逐字段对照 Jev 的能力：

抽取字段Jev 原语适配说明
activity 八分类Choice完美睡眠/工作/学习/健身… 天然的选择题
recordType（过去/未来/状态）Choice完美
periodHint 时段Choice完美早/午/晚/凌晨
心情有无 + 强度Noul + Score完美校准概率可直接作为每域 confidence，优于让 LLM 自报 0.9
财务：有金额/收支方向/分类Noul + Choice完美金额数值本身由确定性引擎（duration.ts）解析，不需模型
饮食：是否适用 / 餐次Noul + Choice完美
人名 / 交易对象抽取—不能开放词汇，闭集原语无法表达，仍需 LLM 或规则
title 短语 / 低置信追问—不能文本生成任务
周/月复盘、陪伴对话—不能本就是 LLM 主场

结论：约六成抽取字段是 Jev 的主场，且直击本项目两大痛点——晚高峰免费档拥塞（毫秒级决策无排队）与置信度不可靠（原生校准概率）。

7.1 已替你验证过的事实（2026-09-19）

  • 国内直连可用：从腾讯云生产服务器实测 api.typesafe.ai（HTTP 404 = 主机可达）、docs.typesafe.ai（308）、typesafe.ai（200）全部直连成功，不存在 OpenAI 式封锁。
  • 成本可忽略：按本项目月约 1.7M 输入 token 估算，Jev 月成本 ≈ ¥0.5，与当前免费的 glm-4.7-flash 同一量级。
  • 架构可承接：本项目的确定性引擎（时长/金额/时间推断）与语义抽取已解耦，未来若引入 Jev 只替换语义分类那一半，五域「拆原子问题」的设计与 Jev 官方最佳实践同构。

7.2 结论与行动建议

当前不接入。理由：① 中文能力无任何实测佐证；② 模型上线仅数日，生产依赖风险过高；③ 只能覆盖六成字段，却要引入第二家 AI 依赖（人名/标题仍需 LLM，变双引擎）；④ 本项目当前真正的痛点（免费档拥塞）用 glm-4.7-flashx 付费档（月 1~2 元）即可解决，性价比更高。
  • 观察信号：中文实测报告出现；HuggingFace 复刻版出现中文可用版本；国产厂商（智谱/DeepSeek 等）跟进同类「决策模型」。
  • 试点路径：现成的 42 句 PoC 测试集（docs/07）就是验收基准——哪天决定试，将五域闭集字段改写成 Choice/Score/Noul 问题组跑一轮准确率对照即可，预计半天工作量。
