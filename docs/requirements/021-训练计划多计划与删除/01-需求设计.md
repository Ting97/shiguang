# 021 · 训练计划多计划与删除 · 需求设计

> 状态：开发中 · 2026-10-16 · 前置：016（健身模块）/ 020（截图导入）

## 背景与目标

训练计划此前是「一天一模块一条」：同日同模块再导入会覆盖草稿（confirmed 后直接 409），也没有删除入口——误导入的计划只能跳过占位。实际使用中一天两练（晨跑 + 晚力量、甚至两节力量课）与截图/文本重复导入都很常见。本批放开并存限制并补删除能力。

## 需求清单

| # | 需求 | 验收 |
| --- | --- | --- |
| FR-A1 | 同日同模块允许多条训练计划并存（迁移 058 去唯一约束；POST /plans 改纯新增，废止 create-or-replace 与 confirmed 409） | 同日两次导入力量课 → 两条计划各自显示、各自联动行动互不影响；今日/计划页均按列表渲染 |
| FR-A2 | 计划可删除：任意状态（draft/confirmed/done/partial/skipped）均可删，入口在计划卡操作区，需确认弹窗 | 删除后计划卡消失；联动的今日行动一并清理（含已完成）；越权 404 |
| FR-A3 | 删除不破坏训练历史：已打卡计划删除后，执行记录保留为独立打卡历史（plan_id 置空），趋势统计不受影响 | 删除已打卡计划后：行动清零、日志仍在且 plan_id=null、actual 原样 |

## 边界与非目标

- 训记（SynFit）侧已同步的训练不随拾光删除回滚（跨系统写操作，保留由用户在训记 App 自行处理；确认弹窗有提示）。
- 不做计划排序/拖拽：多计划按创建顺序展示（listPlans 排序补 created_at）。
- 打卡执行记录暂不提供独立删除入口（本批只动计划）。

## 决策记录

1. **删除语义靠既有 FK 级联，不写业务清理 SQL**：053 建表时 `todos.fitness_plan_id → on delete cascade`、`fitness_session_logs.plan_id → on delete set null` 已是目标语义——删除计划 = 一句 `delete from fitness_daily_plans`，行动全清、日志转独立历史由数据库保证。
2. **确认弹窗而非 window.confirm**：与打卡/训记弹窗同交互形态；按状态差异化文案（已打卡→提示记录保留；已同步训记→提示训记不受影响）。
