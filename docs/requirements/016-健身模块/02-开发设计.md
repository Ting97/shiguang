# 016 · 健身模块:02 开发设计(2026-10-14)

> 架构取向(与用户确认):录入=粘贴文本+AI 解析;生成=聊天助手 + A.5 确认卡;打卡=计划页表单;助手只读工具同期接入;计划自动联动今日行动。

## 一、数据模型(迁移只增不改)

### 053-fitness-module.sql

```sql
fitness_modules      (code text pk, name, icon, sort int, is_active bool)          -- 种子 run/strength
fitness_profiles     (user_id uuid pk→profiles, height_cm int, baseline jsonb,
                      experience text, equipment jsonb, weekly_days text, constraints text,
                      created_at/updated_at)
fitness_goals        (id uuid pk, user_id→profiles, module_code→fitness_modules, title,
                      target_date date, status check(active/achieved/archived),
                      targets jsonb, baseline jsonb, strategy jsonb, created_at/updated_at)
                      -- partial unique (user_id,module_code) where status='active'
fitness_daily_plans  (id uuid pk, user_id, plan_date date, module_code,
                      source check(ai/import/manual), status check(draft/confirmed/done/partial/skipped),
                      content jsonb, rationale text, origin_conversation_id uuid null,
                      created_at/updated_at, unique(user_id,plan_date,module_code))
fitness_session_logs (id uuid pk, user_id, log_date date, module_code, plan_id uuid null→plans,
                      actual jsonb, fatigue int check(1..10), sleep_h_x10 int, soreness text,
                      note text, entry_id uuid null,  -- 二期一句话识别预留
                      created_at/updated_at)
fitness_body_metrics (id uuid pk, user_id, measured_on date, weight_g int, waist_mm int,
                      body_fat_pct_x10 int, resting_hr int, note text, created_at/updated_at,
                      unique(user_id,measured_on))
fitness_exercises    (id text pk, module_code, name, muscle_primary jsonb, muscle_secondary jsonb,
                      equipment text, level text, benefit text, default_template jsonb, sort int)
                      -- 全局种子,不挂 user
todos 加列            fitness_plan_id uuid null references fitness_daily_plans(id) on delete cascade
                      + 索引 idx_todos_fitness_plan
```

单位纪律(AGENTS「金额分」同款整数纪律):距离 **m**、时长/配速 **s**(配速=秒每公里)、体重 **g**、腰围 **mm**、体脂 **×10**、睡眠 **小时×10**。

## 三、packages/ai(纯包,只加常量)

- `schema.ts`:`FitnessPlanDraftV2`(zod)——粘贴解析端点的 AI 输出契约:`{ run: RunPlanContent | null, strength: StrengthPlanContent | null, confidence }`,superRefine:两组全空拒绝;距离/配速/重量入参单位为模型友好的 km/min/'ss"/kg,api 侧映射成整数口径(m/s/g)。
- `prompt.ts`:`FITNESS_PLAN_PARSE_PROMPT`(粘贴佳明文本→结构化课表:课型判定/分段拆解/配速换算 5'50"→350 秒每公里,含金标准示例);`CHAT_ASSISTANT_SYSTEM_PROMPT` 追加「健身教练」节。

## 四、apps/api `src/server/fitness/`(新域,老三样)

- `repo.ts`(全部参数化 SQL):profile upsert/get;goals CRUD;plans 按 user+date(+module) 查、create-or-replace、patch 状态;logs 插入/区间查;metrics upsert/区间查;exercises 目录;**todos 联动 SQL**(按 fitness_plan_id 删未完成/插入行动/置完成,activity_id 挂用户 'fitness' 预设行,复合外键 (activity_id,user_id) 同 todos DDL)。
- `service.ts`:手写校验(ApiError)+ 调 repo;`syncPlanTodos(plan)` 单一规则实现;`parsePlanDraft(text)` 调 glm.chat(经 `ai/prompts.ts` 纳管的 `fitness_plan_parse`,DB 热更)。
- `index.ts`:`export * from "./service"`(跨域只准走 index)。
- 路由(`src/app/api/fitness/**`,全 withAuth/withAuthParams/withAuthSchema):

| 端点 | 说明 |
| --- | --- |
| GET /api/fitness/modules | 模块目录 |
| GET/PUT /api/fitness/profile | 基本情况 |
| GET/POST /api/fitness/goals, PATCH /api/fitness/goals/[id] | 目标(strategy 随 POST 全量替换) |
| GET /api/fitness/plans?from=&to= | 区间日计划(plan_date 北京) |
| POST /api/fitness/plans | create-or-replace 草稿;已 confirmed+ 的 409 |
| PATCH /api/fitness/plans/[id] | 确认/编辑 content/置 skipped/打卡 done+actual |
| POST /api/fitness/plans/parse | {text} → AI 结构化草稿(不入库) |
| GET/POST /api/fitness/logs | 执行记录(独立补录) |
| GET/POST /api/fitness/metrics | 身体指标(upsert measured_on) |
| GET /api/fitness/exercises?module= | 动作库 |

### 今日行动联动(syncPlanTodos)

1. 删除该 plan 未完成行动(`status='pending' and fitness_plan_id=$`)。
2. 计划 skipped/已删 → 到此为止。
3. 力量:父任务(kind='todo',title=content.title,due_at=plan_date 18:00+08,source=ai/manual,activity_id='fitness',fitness_plan_id)+ 每动作子行动(kind='action',parent_todo_id,标题「名称 重量kg×组×次」,sort 递增)。
4. 跑步:单条独立行动(kind='action',标题「title · 总距离km」)。
5. 打卡 done/partial(PATCH /plans/[id])→ `update todos set status='done', done_at=now() where fitness_plan_id=$ and status='pending'`。
6. 首页今日行动与助手 `query_todos` today_actions 视图按 due_at 口径自动带出,零改动。

### 提案工具(A.5 首发落地)

- 新增独立注册表 `CHAT_PROPOSAL_TOOLS`(与只读 `CHAT_TOOLS` 同构但分离,只读注册表红线不破)。`toAgentTools` 合并两表;`TOOL_LABELS` 补条目。
- `propose_fitness_plan`:params zod `{ planDate(YYYY-MM-DD,服务端校验=北京今天/明天), moduleCode(run/strength), content(同 §二结构,含每动作 exerciseId/name/sets/reps/weightKg/rir), rationale }`。execute 只 insert chat_proposals(kind='fitness_plan',status='pending',payload 含全部参数),返回 `{ proposalId, saved: false, hint: "已生成计划卡片,等用户确认后才会保存" }`。
- `GET /api/chat?id=`:响应体在既有 `{conversation,messages,hasMore,oldestId}` 上增 `proposals`(本会话近 20 条,含 pending/accepted/dismissed 与 createdAt)。
- `POST /api/chat/proposals/[id]`:`{action:'dismiss'}` → dismissed;accept 由前端直接调 `POST /api/fitness/plans`(payload)成功后再调 proposals accept——**确认动作复用业务域 API,不另开后门**。
- chat-core.tsx:消息流内渲染 pending 卡片(模块徽标/日期/动作明细,每动作一行:名称 组次 重量 + 肌群 + benefit/理由),按钮「保存计划」「放弃」;已决卡片显示状态角标。

### 提示词

`CHAT_ASSISTANT_SYSTEM_PROMPT` 追加:

- 健身教练节:训练问题先调 fitness 工具;跨模块安排严格按 get_fitness_goals 返回的 strategy.adjustProtocol(质量课当天不练腿、长距离前一天只上肢、睡眠<6h 降级、连续 6 天强制休息);推荐动作引用动作库肌群收益;要落地必须调 propose_fitness_plan 并等用户点卡片确认,严禁声称已保存。
- 部署检查:生产 `ai_prompts` 若存在 chat_assistant 启用中覆盖,同步更新 DB 文案。
