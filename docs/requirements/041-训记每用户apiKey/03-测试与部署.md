## 二、踩坑记录

1. **多账号读缓存隔离是隐蔽高危点**：训记 90s 按日读缓存原以 datestr 为键，若只加 key 参数不分桶，A 账号当日数据会串给同日查询的 B 账号——缓存键已改 key 指纹前缀并配了专门用例（两 key 同日各自外呼各归各）。
2. Node `crypto` GCM 顺序：`getAuthTag()` 必须在 `final()` 之后调用（造测试数据时反了报 "Invalid state for operation getAuthTag"）。
3. apikey invalid 的用户文案从「更新 .env」改为「【我的 → 训记同步】重新绑定」——既有断言 `/重新申请/` 同步更新。

## 三、部署记录（2026-10-23）

- `node scripts/deploy.mjs` 全流程通过：pg_dump 备份 → 迁移 068 生产执行 → 双 tar → 原子交换 → 冒烟（health ok / login 200 / me 401）。
- **线上存量 key seed**：部署后把生产 .env 的 XUNJI_API_KEY 以生产 EXCHANGE_ENC_KEY 加密写入 15091587905 用户名下（经隧道参数化 SQL，密钥经 ssh 读取不回显）——该用户同步/回读/助手查询体验不变；其余用户首次使用前在【我的 → 训记同步】绑定自己的 key。
- 用户操作路径：【我的 → 训记同步】粘贴训记 App「我的 → 设置 → Open API」申请的 key 点绑定；健身页计划卡的「同步训记 / 回读打卡」即按本人账号工作。
