## 1. 背景与定位

本包是对**已上线**（Web+API，2026-09-22）的 001 需求包中 **R3 目标空间**的增强与补充，外加一条全站生效的交互规范：

- **N1 待办手动关联空间**：001 的 FR-3.4 已含"创建时可选空间、行显示徽标、可修改"，本包把**存量待办的手动关联/切换/移除**交互明确为正式需求（用户侧入口清晰化），并补齐归档空间的关联规则；
- **N2 空间感悟**：全新子模块——宏大目标的推进过程中用户会有想表达的内容（阶段心得、踩坑复盘、自我对话），给空间一个长文记录位（单篇 ≤5 万字）；
- **N3 浮层点击空白关闭**：全站交互规范——所有软性弹窗/就地编辑，点击其余空白处自动取消关闭，降低关闭成本、统一心智；
- **N4 空间名称就地编辑**：明确空间名称可随时编辑（含就地重命名交互）；修改接口 001 已上线，本包补前端交互。
- **N5 全项目术语统一**：两级任务名称全项目统一——一级叫 **todo**、二级叫 **行动**，全站用户可见文案替换（原 003 需求包并入）。
- **N6 行动解耦**：行动从"必须挂在 todo 下"解耦为可独立存在；首页今日行动清单从只读变为可直接添加行动（原 003 之后新增，同日并入）。

> **实施分批**：2-A = N3（浮层统一关闭）+ N5（术语统一），零迁移纯前端/文案可先行；2-B = N1/N2/N4（感悟表走迁移 026，001 的 022~025 已在生产执行）；2-C = N6（迁移 027）。2-A / 2-B / 2-C 之间无强依赖，顺序可互换，建议 2-A 先行快赢。

## 3. N1 待办手动关联空间

### 3.1 现状与用户故事

001 设计已支持：创建待办时选空间、`PATCH /api/todos/[id] {spaceId}` 修改、AI 识别的待办继承动态空间。用户故事：

- 作为用户，我之前随手记的待办（没选空间）做完一半才意识到它属于"上岸"这个空间——我想在待办行上直接把它挂进去，不用进编辑态。
- 作为用户，我把待办挂错空间了，想直接在行上切换到正确的空间，或移除关联。

### 3.2 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-N1.1 | 行级关联入口 | 待办看板（/schedule）与空间详情页的**顶层待办行**提供「关联空间」操作（行操作组 🎯 按钮）：弹出空间选择浮层（列出 active 空间 icon+名称，含「移除关联」项） |
| FR-N1.2 | 关联/切换/移除 | 点选空间即关联或切换（行上空间徽标即时更新）；「移除关联」清空 spaceId；浮层点空白即关闭（遵循 N3） |
| FR-N1.3 | 徽标展示 | 已关联待办行显示空间徽标（icon+名称 tinted chip，空间 color 定色）；点击徽标快捷打开关联浮层；关联到已归档空间的，徽标加置灰态仍可展示/移除 |
| FR-N1.4 | 行动随父 | **有父**行动不单独关联空间，空间归属随父待办；**独立行动**（N6，无父）可像 todo 一样关联/切换/移除空间（顶层行，同一条 PATCH）；今日行动清单不展示空间徽标（父待办名已是上下文） |
| FR-N1.5 | 服务端校验 | `PATCH /api/todos/[id] {spaceId: uuid|null}`：空间必须属于当前用户（不要求 active——归档空间允许保留/清除，但不允许新关联到归档空间）；**有父**行动拒绝单独改空间（409），独立行动允许 |

### 3.3 验收标准

- [ ] 待办行可关联/切换/移除空间，徽标即时更新，无需进编辑态
- [ ] 空间选择浮层点空白自动关闭（N3）
- [ ] 归档空间：徽标置灰可见、可移除、不可新关联
- [ ] 有父行动改空间返回 409、行动行无关联入口；独立行动（N6 后）可关联空间（徽标带「行动」标识）
- [ ] 关联后空间详情页的待办列表与统计（待办数/完成率）同步变化

## 4. N2 空间感悟

### 4.1 概念定义

**感悟**：用户在某个目标空间内记录的自由表达内容——阶段心得、复盘、自我对话、引用摘抄等。纯文字、纯手动（本期不接 AI 生成），**单篇上限 50,000 字**，可编辑、可删除，按时间线倒序展示。

### 4.2 用户故事

- 作为用户，备考三个月后我想写一篇长文记录心态变化，挂在"上岸"空间里，一年后回看这是一条完整的心路。
- 作为用户，我偶尔只想写两三句话的碎念，也能随手记进空间。
- 作为用户，写错的感悟我可以改，不要的可以删。

### 4.3 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-N2.1 | 入口与列表 | 空间详情页新增「感悟」区（与"待办/动态"并列的 tab 或分区）：时间线倒序列表（日期 + 内容预览截断），「写感悟」按钮新建；分页加载（每页 20） |
| FR-N2.2 | 编写 | 底部抽屉/弹层编辑器：自适应高度 textarea、实时字数统计（x/50000）、手动保存；超 5 万字禁止保存并提示 |
| FR-N2.3 | 编辑与删除 | 列表点条目进入编辑（同一编辑器，回填内容）；删除需确认；编辑更新 `updated_at`，列表按创建时间排序、显示"已编辑"标记 |
| FR-N2.4 | 长文性能 | 列表接口只返回预览（前 300 字）+ 总字数；点开/编辑时拉取全文，保证长列表流畅 |
| FR-N2.5 | 数据与校验 | `content` 非空、≤50000 字（服务端 `char_length` 硬校验 + 客户端预校验）；仅本人可读写（与全站数据归属一致） |

### 4.4 边界与异常

- 感悟随空间删除级联删除（`on delete cascade`）——删除空间二次确认文案提示"含 N 篇感悟"。
- 归档空间的感悟保留可见可写（归档≠冻结，用户可能翻旧账写总结）。
- 编辑器打开状态下点空白**不**自动关闭？——**遵循 N3 自动取消**，但保存按钮常驻、且自动关闭前若内容有改动，底部 toast 提示"已取消，未保存"（不弹确认，保持轻量；用户要求自动取消语义优先）。
- 5 万字边界：客户端按字符计数（与 DB `char_length` 同口径），粘贴超限立即截断提示。

### 4.5 验收标准

- [ ] 空间详情页可写/看/改/删感悟；列表预览截断 + 点开看全文
- [ ] 单篇 ≤50000 字：客户端计数正确、超限禁止保存、服务端拒绝（>50000 返回 400）
- [ ] 编辑后显示"已编辑"，排序仍按创建时间倒序
- [ ] 删除空间时感悟级联删除且确认文案含数量
- [ ] 他人/未登录无法访问感悟接口（401/403）
- [ ] 感悟编辑器遵循 N3（点空白取消 + 未保存提示 toast）

## 5. N3 浮层点击空白关闭（全局交互规范）

### 5.1 规范定义

**所有"软性"浮层**——下拉菜单、弹出选择器、底部抽屉、就地行内编辑器、确认对话框——在用户点击浮层**以外的空白区域**时自动执行"取消/关闭"（不保存编辑内容、不执行浮层内动作）；按 `Esc` 键等效。

**豁免清单**（不自动关闭）：

| 场景 | 原因 |
|---|---|
| 进行中任务浮层（图片上传进度、AI 拆解 loading） | 关闭可能丢失任务上下文；由任务完成/失败驱动关闭 |
| 全屏浏览态（图片 Lightbox） | 无"外部空白"概念，维持点击遮罩/Esc 关闭 |
| 登录页等整页表单 | 非浮层 |

### 5.2 用户故事

- 作为用户，我点开一个菜单后发现不需要，直接点旁边任意位置就能关掉，不用去找 × 或再点一次菜单按钮。
- 作为用户，我展开一行编辑又不想改了，点一下页面别处，编辑自动收起。

### 5.3 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-N3.1 | 统一关闭行为 | 全站所有软性浮层：`pointerdown` 落在浮层外 → 立即取消关闭；`Esc` → 取消关闭；两者等效 |
| FR-N3.2 | 统一实现 | 通过公共组件/钩子（`Dismissable` / `useDismiss`）统一实现，禁止各浮层自写 document 监听；新浮层一律使用 |
| FR-N3.3 | 存量改造 | 现存浮层逐个接入：待办行内编辑器（todo-board/今日行动清单）、entry-menu 识别菜单、publish-sheet 发布抽屉、icon-picker、活动分类编辑、账户/账单相关菜单，及 001/002 新增浮层（空间关联浮层、空间编辑弹层、感悟编辑器、admin 对比弹层等） |
| FR-N3.4 | 取消语义 | 就地编辑取消 = 不保存改动并收起；菜单/选择器取消 = 关闭无副作用；确认对话框取消 = 关闭且不执行操作（危险操作仍以按钮确认为准，点空白只是关掉） |
| FR-N3.5 | 未保存提示 | 行内/浮层编辑器内容有改动且因点空白/Esc 取消时，toast 轻提示「已取消，未保存」（不打断、不弹二次确认） |

### 5.4 边界与异常

- 打开浮层的同一次点击不得立刻触发关闭（监听挂载时序保证：监听在挂载后下一次 `pointerdown` 生效）。
- 移动端 PWA：底部抽屉保留遮罩点击关闭（与空白点击语义一致）；滚动穿透在浮层打开时锁定 body 滚动（现状已有则沿用）。
- 输入法组合中（IME composing）的点击照常触发关闭（取消语义明确）。
- 一次只允许一个同级浮层：打开新浮层时自动关闭旧浮层（如从关联浮层再打开编辑）。

### 5.5 验收标准

- [ ] 上述存量 + 新增浮层逐一验证：点外部空白关闭、Esc 关闭、关闭后无副作用
- [ ] 编辑器取消不落库，且内容有改动时出现「已取消，未保存」toast
- [ ] 豁免清单场景不被误关（上传中/AI 拆解 loading 保持）
- [ ] 打开浮层的点击不会立即把它关掉；嵌套浮层互不误关
- [ ] 移动端 PWA 与桌面行为一致

## 7. N5 全项目术语统一

### 7.1 背景与术语标准

001 v1.1 已把"子任务"更名为**行动**，但一级任务的叫法在产品各处仍混用"待办 / TODO / 任务"。本需求把两级任务的名称**全项目统一**，作为长期术语标准：

| 层级 | 统一名称 | 弃用词 |
|---|---|---|
| 一级任务 | **todo**（小写原词，中文语境直接嵌入，如"今日 todo""添加 todo"） | 待办、任务、UI 展示层大写 TODO |
| 二级（todo 之下，仅一层） | **行动** | 子任务、子待办 |

统一收益：用户心智一致（界面、提示、文档同一种叫法）；与代码层天然对齐（表名 `todos`、类型 `TodoRow`、路由 `/api/todos` 本来就是 todo，消掉中英错位）。

### 7.2 用户故事

- 作为用户，我在任何页面看到的都叫 todo / 行动，不会一会儿"待办"一会儿"TODO"。
- 作为用户，AI 的提示文案（"AI 正在识别…待办…"）和界面标签（"todo"）说的是同一个东西。

### 7.3 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-T1 | 术语表落地 | 上表作为全项目文案规范，此后新界面/新文档/新 prompt 一律遵循（code review 检查项） |
| FR-T2 | "待办"→"todo" | 全部用户可见文案替换（约 60+ 处：Web 16 个文件、Expo App 3 处、API 消息 3 处、shared 提醒横幅 1 处）；组合词按映射表（02 设计 §7.2）自然替换，如"今日待办→今日 todo""待办完成率→todo 完成率" |
| FR-T3 | 大写统一小写 | UI 展示层的 "TODO" 统一小写（schedule tab、副标题"日历 · TODO · 分类"、"日程 · TODO" ×2） |
| FR-T4 | "子任务/子待办"→"行动" | 用户可见处（todo-board 展开按钮 title"收起/展开子任务"）必须改；注释中 9 处顺带改（P2） |
| FR-T5 | 纯文案变更 | 不改任何逻辑、接口、数据；替换后全站主要路径回归不受影响 |

范围分级：**P1 必须** = 用户可见文案（Web 界面字符串、Expo 文案、API 返回 message、shared 渲染给用户的横幅 label）；**P2 建议** = 代码注释、复盘 prompt 素材词（"完成待办：N 件"→"完成 todo"，AI 小结输出口径随之统一）、docs 术语；**不改** = 代码标识符与协议（`todos` 表、`TodoRow/TodoItem` 类型、`/api/todos` 路由、`view` 参数值、intent key `"todo"`、git tag、DB 数据）。

### 7.4 边界与异常

- 组合词按映射表替换，保证语法自然，不做机械逐字替换；中英混排与现状排版习惯一致。
- AI 生成的复盘小结内容本身不保证用词（LLM 输出），prompt 素材词统一后输出口径趋同，不在验收范围。
- 历史文档（已归档的 001 文档）与已入库的 `review_caches` 历史缓存不回改，新文档遵循术语表。
- 代码备忘注释（`TODO:`）与文件名（todo-board.tsx 等）属标识符层，不改。

### 7.5 验收标准

- [ ] Web / Expo / API 消息中用户可见的"待办"清零（grep 硬验收）
- [ ] 用户可见的"子任务/子待办"清零
- [ ] UI 展示无大写 "TODO"（tab、副标题、引导文案均为小写 todo）

## 8. N6 行动解耦：行动可独立存在，今日行动可直接添加

### 8.1 背景

现状（001 已上线）：行动必须挂在某个 todo 之下（子待办，`parent_todo_id` 非空），首页「今日行动清单」是**只读**视图——里面的行动全部来自 todo（每日重复行动，或父待办标记今日/今日到期的行动）。想记一条与任何 todo 都无关的一句话小事（"给老师发条消息"），要么硬建一个 todo，要么没地方放。

本需求把 todo 与行动**解耦**：

- **行动**成为可独立存在的最小执行单元（不挂任何 todo）；
- **todo 可有多个行动**——现状能力，保持不变；
- 首页今日行动清单从只读变为**可直接添加行动**。

### 8.2 用户故事

- 作为用户，我突然想起"给老师发条消息"这种一句话小事，不值得建 todo——直接在首页今日清单里加一条行动，做完勾掉。
- 作为用户，我建的独立行动和 todo 拆出来的行动待遇完全一样：能设每日重复并累计完成次数、能标记今日/重要、能设到期时间、能 AI 拆解。
- 作为用户，我的 todo 继续挂多个行动（现状），互不影响。

### 8.3 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-N6.1 | 首页添加行动 | 今日行动清单提供「添加行动」输入行（样式对齐 todo-board 添加行）：回车即建；新建行动**默认标记今日**（当日出现在清单）；创建后可再设置重复/重要/时间 |
| FR-N6.2 | 行动独立存在 | 行动可不挂任何 todo 独立创建与存在；独立行动与 todo 拆出的行动能力完全一致：勾选完成、每日重复 + 已完成次数、⭐/☀️ 标记、到期时间、编辑/删除、AI 拆解（产出同为独立行动） |
| FR-N6.3 | todo 多行动（确认不变） | 一个 todo 下仍可有多个行动（现状能力）；**行动之下仍不可再有行动** |
| FR-N6.4 | 今日清单规则 v2 | 清单 = 行动级条目：① 每日重复行动；② **独立行动**中被标记今日/今日到期者（含首页新建的默认今日行动）；③ 有父行动中父待办标记今日/今日到期者（现状规则不变） |
| FR-N6.5 | 看板可见性 | 独立行动在 /schedule 看板的 全部/已完成/今日/重要 视图中带「行动」徽标可见（不产生管理盲区），视图计数徽标同步；空间详情页同理（若关联了空间） |
| FR-N6.6 | 纯增量 | 不改变现有 todo/行动的数据与行为；存量数据仅加 kind 列 + 回填，零业务迁移 |

### 8.4 边界与异常

- 独立行动不可再挂行动（服务端校验父必须为 todo；看板对独立行动行不提供"添加行动"入口）。
- AI 识别产物仍为 todo；AI 拆解待办产生的行动仍挂父；**AI 不直接创建独立行动**（拆解独立行动时产出独立行动，见 02 §8.2）。
- 独立行动默认无空间归属，可手动关联空间（衔接 N1：有父行动随父的约束不变）。
- 独立行动的每日重复沿用 06:00 惰性恢复、同记录日计数去重；删除独立行动即物理删除。
- 首页新建行动在无网络时行内报错保留输入（与现有添加行行为一致）。

### 8.5 验收标准

- [ ] 首页今日清单可直接添加行动：回车即建、当日出现在清单、可连续添加
- [ ] 独立行动可勾选/编辑/删除/设每日重复/设今日/设重要/设到期，×N 计数正确，06:00 日切恢复
- [ ] 独立行动可 AI 拆解：产出 ≤3 个独立行动插入其后，原行动保留
- [ ] todo 添加多个行动不受影响；给任何行动（有父/独立）添加子行动被拒绝（409）
- [ ] 看板 全部/今日/重要/已完成 视图中独立行动带「行动」徽标可见，四视图计数徽标正确
- [ ] 存量数据回归无变化（旧 todo/行动行为与展示不变）
