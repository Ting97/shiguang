## 1. 背景

### 1.1 项目现状规模（2026-09-23 全库调研）

拾光已从 Phase 0 的 PoC 成长为**生产运行中的四轴经营系统**（时间 · 目标 · 人际 · 财务 + AI 内核）：

- **apps/api**：97 个 TS 文件、约 9,538 行；70 个 route 文件；`src/lib` 22 个文件承载全部业务逻辑；手写 SQL（pg 直连，11 处手管事务）；无 ORM、无 schema 校验库、无请求日志。
- **apps/web**：64 个 tsx、约 14,300 行、39 个组件；纯静态导出；**无状态管理库**，408 处 `useState` / 103 处 `useEffect`；裸 `fetch` 约 112 处 vs 统一封装 `api()` 仅 37 处并存。
- **packages/ai**：设计成熟的自研内核（zod 契约 + LLM 主干 + 确定性防漂移 + 规则兜底 + 审计计量），零 SDK 手写 HTTP。
- **packages/db**：33 个手写 SQL 迁移，**无迁移运行器、无迁移记录表**，按部署文档手工 psql 执行。
- **测试**：api 4 个纯函数单测（174 行）、shared 5 个、ai 4 个；**70 个路由零测试，web UI 层零测试**。
- **工程**：无 ESLint / Prettier / CI；无 AGENTS.md（本项目由"单人 + AI 编码代理"协作开发，git log 佐证）。

### 1.2 核心痛点（证据见 §11 附录）

1. **无领域边界**：业务逻辑平铺在 `lib/` 与 route handler 里，SQL 即业务。跨域写入（五域识别 confirm 落四张域表）与跨域读取（复盘读全库）无显式契约，改一张表不知道波及谁。
2. **重复代码规模化**：`getCurrentUser()+401` 模板 95 处/66 文件；`checkAiQuota` 话术 9 处逐份复制；北京时间工具 4 份；MIME 表 2 份；sms/email 验证码通道近乎复制；`GLM_MODEL` 默认值 8 处硬编码。
3. **安全隐患**（详见 §5-C）：`AUTH_DISABLED=1` 万能后门反射任意 Origin；登录无尝试限制可暴力破解；无 CSRF token；`/api/auth/setup` 存在抢占窗口；审计写入静默失败导致配额可能漏计。
4. **巨型文件**：后端 `review-ctx.ts` 524 行；前端 Top10 全部 350+ 行（最大 `spaces/[id]/detail.tsx` 1258 行），单文件承载取数+状态+UI+弹层。
5. **前端数据层双轨**：统一封装与裸 fetch 并存，401 跳登录散落 11 处，无全局错误边界，无统一会话 hook；mobile 与 web 零代码共享。
6. **AI 内核缺陷**：`jev-shadow.ts` 存在已修过同款的时区 bug（本地 getter 二次 +8）；Jev 问题组两份维护；规则兜底引擎硬编码演示人名（老王/爸妈/小李）；`extractJson` 双实现；ASR 无重试；429 判定靠错误字符串匹配；熔断状态是单进程内存变量。
7. **变更不可观测**：无结构化日志、无请求日志、无请求 ID；排障靠 Caddy 访问日志 + stderr。

### 1.3 为什么是现在

003 包（3-A AI 输入装配、3-B/3-C Jev 接入与影子）上线后，AI 编排层（prompts/ai-inputs/jev-shadow/analyze）已成为 lib 层最厚的部分；业务域数量（动态/日程/待办/空间/财务/负债/人际/复盘）已到 8 个。**继续在无边界结构上叠加，每次新域的边际成本都在上升**。趁 Phase 4 迭代间隙做一次结构性还债，是成本最低的窗口。

## 2. 重构目标

三大支柱（对应用户提出的"健壮性、安全性、可扩展性"）：

| 支柱 | 含义 | 达成手段（对应需求部分） |
|---|---|---|
| **健壮性** | 错误被分类处理、行为可观测、变更有测试护栏、故障可快速回滚 | A 统一 API 基座 + F 测试与 CI + G 可观测性 |
| **安全性** | 认证通道无暴力破解面、无后门、防 CSRF、审计可靠 | C 安全加固（专项） |
| **可扩展性** | 新业务域按模板接入而不改存量；换/加 AI 供应商零散弹；前端新页面复用数据层与 UI 基建 | B 领域模块化 + D AI 内核重构（Vercel AI SDK）+ E 前端重构 |

**总纲**：采用**模块化单体（modular monolith）**演进，不做微服务；对外 API 路径与行为保持兼容（strangler 渐进替换）；数据零丢失、线上不停机。

## 3. 用户故事

- 作为**本项目的唯一开发者**，我想新增一个业务域（如"健康"）时只需按既有模板建目录、写 service/repo、注册路由，而不需要通读 9,500 行 api 代码——因为边界清晰、模板现成。
- 作为**开发者**，我改了财务相关表后想知道会波及哪些调用方——因为跨域访问只能走显式 service 接口，grep 一个导出名即可。
- 作为**开发者**，我希望 70 个路由里不再有 95 份复制的鉴权模板，新增路由时不可能忘记鉴权/校验/错误处理——因为高阶封装强制约定。
- 作为**运维者（同人）**，线上出问题时我能按请求 ID 串起一次请求的完整日志，看到它调了哪个 AI 能力、花了多少 token——而不是翻 Caddy 日志猜。
- 作为**用户**，我的账号即使被拖库字典攻击也不会被暴力撞开——登录有锁定与限流。
- 作为**用户**，即使服务器进程重启，我发的动态的后台识别不会静默丢失。
- 作为**AI 编码代理的驾驭者**，仓库里有 AGENTS.md 告诉每个代理怎么构建、测试、遵循什么规范，代理产出直接过 CI——开发提速且不引入野代码。
- 作为**管理者**，我想在 Claude Code / Cursor 里直接问"我这周花了多少钱、和老王见了几次"——通过 MCP 接口消费自己的系统。

## 5. 功能性需求详述

### 5-A 工程基座（FR-A）

- **FR-A1.1** 提供路由高阶封装：`withRoute(handler)`（统一 try/catch → ApiError 映射、请求日志、requestId 生成）、`withAuth(handler)`（注入 `user`，未登录统一 401）、`withAdmin(handler)`、`withAiQuota(capability)`（统一 402 升级话术）。全部 70 个路由分批迁入，迁入后路由文件只做"解析入参 → 调 service → 返回"。
- **FR-A1.2** 错误规范：`ApiError(status, code, message, detail?)` 统一错误响应体 `{ error, code }`；现有 19 处手写 500 收敛为分类错误（参数/权限/冲突/依赖不可用）。
- **FR-A1.3** 入参校验：所有写操作路由入参经 zod schema 校验（schema 与 packages/shared 类型同源），替代手工 if+正则。
- **FR-A2.1** `src/server/config.ts` 集中读取并校验全部 env（DATABASE_URL、AI keys、SMS/SMTP、JEV_MODE 等）；缺失必需项时启动失败并给出明确清单。
- **FR-A2.2** 生产环境（NODE_ENV=production）下：`AUTH_DISABLED` 非空即拒绝启动；`DATABASE_URL` 含弱口令默认值即拒绝启动（显式 `ALLOW_INSECURE=1` 才可越过并打警告）。
- **FR-A3.1** migration runner：`npm run db:migrate` 按 `schema_migrations` 表记录增量执行 `packages/db/migrations/*.sql`；`db:migrate:status` 查看差异；已执行迁移不重复跑。
- **FR-A4.1** 根与各 workspace 增加 ESLint（typescript-eslint 严格集）+ Prettier；CI（GitHub Actions 或等价）跑 lint + typecheck + test + build，红不过合。
- **FR-A4.2** 仓库根 `AGENTS.md`：写明 monorepo 结构、构建/测试命令、代码规范、安全红线（如"禁止引入新 env 时不更新 config.ts"），各 package 可嵌套补充。

### 5-B 领域模块化（FR-B）

- **FR-B1.1** 后端按下列 9 个领域模块重组（详细映射表见 02 §2）：

| 模块 | 业务职责 | 现有表 | 现有路由（迁入） |
|---|---|---|---|
| `identity` 身份与访问 | 登录/注册/会话/验证码/个人资料 | profiles、sessions、sms_codes、email_codes | /api/auth/*（不含 invites） |
| `timeline` 时光流 | 动态采集、五域识别编排、图片、确认流 | entries、entry_recognitions、entry_images、voice_logs、diet_records | /api/parse、/api/feed*、/api/entries/* |
| `time` 日程 | 时间块、活动分类、时长统计 | time_blocks、activities | /api/blocks*、/api/activities*、/api/stats/range |
| `goal` 目标 | 待办/行动、目标空间、感悟 | todos、goal_spaces、space_reflections | /api/todos*、/api/spaces* |
| `finance` 财务 | 账户、流水、预算、导入、复盘报表；负债子域 | transactions、accounts、budgets、liabilities、liability_payments | /api/accounts*、/api/transactions*、/api/budget、/api/finance/*、/api/debts* |
| `people` 人际 | 联系人档案、往来记录、画像 | contacts、interactions | /api/contacts*、/api/interactions/* |
| `insight` 复盘与工作台 | 四级复盘、今日工作台、提醒（跨域读模型） | review_caches、review_gen_quotas、user_ai_profiles | /api/review*、/api/today、/api/reminders |
| `ai` AI 内核 | prompt/输入装配管理、识别管线、影子对照、ASR、计量配额 | ai_prompts、ai_prompt_versions、ai_input_configs、audit_logs | /api/asr、/api/admin/prompts*、/api/admin/ai-mode |
| `platform` 平台 | 邀请码、模块授权、套餐计费、文件、导出、静态托管、健康检查 | invite_codes、user_module_grants、app_config | /api/admin/invites、/api/admin/grants、/api/billing/*、/api/files/*、/api/export、/api/auth/invites（别名） |

- **FR-B1.2** 模块内三层：`route.ts`（薄适配）→ `service.ts`（业务/事务边界）→ `repo.ts`（SQL 唯一发生地）；每模块 `index.ts` 只导出 service 接口作为对外面。
- **FR-B1.3** 依赖规则（CI 可检查）：模块间禁止 import 对方 `repo`/表；跨域写走对方 service（如 timeline 的 confirm 编排调 time/goal/finance/people 的 `confirmXxx`）；`insight` 作为显式 CQRS 读侧允许跨域只读，须集中声明读哪些表。
- **FR-B1.4** `src/lib` 22 个文件按归属拆解进模块或下沉 platform 基建，拆解后 `lib/` 不再存放业务逻辑。
- **FR-B2.1** 重复归一：鉴权模板由 FR-A1 消灭；`bjToday/mondayOf/addDays` 等统一用 `packages/shared/src/date.ts`；MIME 表单源化；`sms.ts`/`email.ts` 合并为验证码通道抽象（`CodeChannel` 接口 + 两实现）；`GLM_MODEL` 默认值单源（并入 FR-D1 配置）。

### 5-C 安全加固（FR-C）

- **FR-C1.1** 登录接口限流：按 `身份标识+IP` 维度滑动窗口限流（如 15 分钟 10 次失败），超限锁定 15 分钟并返回统一模糊文案（不暴露"账号存在与否"）。
- **FR-C1.2** 账号锁定与通知：连续失败达阈值（如 20 次）锁定账号并发邮件/短信通知属主；管理员可解锁。
- **FR-C1.3** 全端登出：`POST /api/auth/logout-all` 吊销该用户全部 session（sessions 表按 user 批量失效），前端个人设置页提供入口。
- **FR-C2.1** `AUTH_DISABLED` 治理：仅 `NODE_ENV≠production` 可用；生产检测到即拒绝启动（与 FR-A2.2 合并实施）；开发模式启用时启动日志显著警告。
- **FR-C2.2** CSRF 强化：对 Cookie 会话的写请求强制校验 `Origin`/`Sec-Fetch-Site`（白名单对齐 CORS），不匹配即 403；Bearer 请求豁免。替代引入 CSRF token 的 heavier 方案（决策记录见 02 §5）。
- **FR-C2.3** setup 抢占防护：`/api/auth/setup` 增加一次性引导令牌（部署时生成，服务器 .env 持有）；且被调用过一次后（无论成败）永久失效。
- **FR-C3.1** audit 写入可靠性：`lib/audit.ts` 失败时重试一次并以结构化 error 日志暴露（不再静默）；连续失败计入健康检查降级信号。
- **FR-C3.2** 配额计数解耦（P2）：免费配额口径从 audit_logs 行数改为独立 `ai_usage` 台账（迁移 036 预分配），与审计日志职责分离。
- **FR-C2.4**（随 FR-B1 顺带）：`parse` 的 fire-and-forget 识别增加落库任务语义（识别产物缺失的 entries 可被巡检补跑，替代纯内存 Promise）。

### 5-D AI 内核重构（FR-D）

- **FR-D1.1** packages/ai 引入 Vercel AI SDK：GLM 与 Jev 客户端收敛到统一 provider 抽象（openai-compatible 对接智谱端点）；`chat → generateText`、`extractJson → generateObject`（zod 契约直接复用）。
- **FR-D1.2** 现有可靠性语义保留：429/5xx 指数退避重试、fallback 模型降级、额度熔断、鉴权/参数错误不重试——迁移后行为等价（用现有 4 个单测 + 新增传输层单测验证）。
- **FR-D1.3** 配置单源：`GLM_MODEL` 等 env 与默认值只在 packages/ai 一处定义，apps/api 8 处硬编码默认值全部改为引用。
- **FR-D2.1** 修复 `jev-shadow.ts` 时区 bug（`+8h 后读本地 getter` 的二次偏移；`hourBucket` 依赖服务器本地时区）——统一走 shared/date 或 toCstWallClock。
- **FR-D2.2** Jev 问题组单源化：`run-jev-poc.ts` 与 `jev-shadow.ts` 两份问题字典合并为单一导出。

## 8. 边界与非目标

- **不做微服务/多进程拆分**：单机部署形态下模块化单体是收益/成本最优解。
- **不更换数据库/不引入 ORM**：手写 SQL + 参数化是现有安全资产，仅加 repo 层收口；是否引入轻量查询构建器留待 005+。
- **不重写 mobile**：Expo App 保持现状，仅做共享层试点（FR-E3）。
- **不做视觉改版**：重构不改变任何用户可见行为与样式。
- **不追求全量覆盖率**：80%+ 对单人项目不成比例，核心域 60% + 三层冒烟为度。
- **Mastra/MCP 中长期项**：MCP 列为 P2 可选（4-H）；Mastra 等出现持久化工作流需求再立项。
