## 1. 调研问题

`packages/ai` 目前是**零 SDK、手写 fetch** 直连智谱 OpenAI 兼容端点的自研客户端（`glm.ts` 230 行：重试、退避、429 降级、熔断、JSON 抽取全部手写）。本次重构需要回答：

1. 是否应该引入 AI 应用开发框架替换手写传输层？引入哪个？
2. 社区主流的 agentic coding 工具与工作流约定（AGENTS.md、spec-driven、MCP），对本项目有什么可借力的？

## 2. AI 应用开发框架（TS 生态）

### 2.1 Vercel AI SDK —— 首选

- **现状**：TS 生态事实标准，当前最新大版本 v7（2026 年中发布，9 月仍在高频 patch）。四年四个大版本（4→5→6→7），官方提供逐版迁移指南。
- **核心能力**：统一 provider 接口（一套 `generateText` / `streamText` / `generateObject` 换模型零改动）、流式输出、tool calling 与工具审批、Agent 抽象、MCP client 支持、`useChat` 等 UI hooks。
- **与本项目的匹配点**：
  - `chat()` / `extractJson()` 与 `generateText` / `generateObject` 一一对应，迁移是**替换传输层而非重写架构**；
  - `@ai-sdk/openai-compatible` provider 可直接对接智谱 `ZHIPUAI_BASE_URL`，与现有 Jev 第二供应商（`jev.ts`）收敛到同一 provider 抽象；
  - `generateObject` + zod 结构化输出，与现有 `FullExtractionV2` zod 契约（`packages/ai/src/schema.ts`）天然契合（AI SDK 经 Standard Schema 支持 zod 3/4，具体版本在 02 §7 对齐）；
  - SSE 流式解析、tool calling 重试这些最容易写错的底层由官方接管。
- **风险**：一年一个大版本的"升级税"——对策：锁版本 + 按官方迁移指南小步跟。
- 出处：<https://ai-sdk.dev/docs/introduction> · <https://github.com/vercel/ai/releases>

### 2.2 LangChain.js / LangGraph.js —— 不采用

仍活跃维护（18.2k star，定位转向 agent engineering platform），LangGraph.js 的图编排在大厂生产有用例；但抽象层厚、概念多（Chain/Retriever/LangSmith 全家桶），对个人项目普遍被认为过重，**复杂度收益不匹配**。出处：<https://github.com/langchain-ai/langchainjs>

### 2.3 OpenAI Agents SDK（JS）—— 不采用

官方 MIT 开源（约 3.9k star）：Agent、handoffs、guardrails、tracing、MCP、Realtime 语音代理。名义 provider-agnostic 但默认面向 OpenAI，生态远小于 AI SDK。仅当需要 OpenAI Realtime 实时语音链路时再评估。出处：<https://github.com/openai/openai-agents-js>

### 2.4 Mastra —— 备选（不现在引入）

TS 原生代理框架，28.3k star，非常活跃：40+ 模型路由、图式 workflow（含 suspend/resume 人机协同与持久化状态）、RAG、evals、MCP server 编写。注意双许可：核心 Apache 2.0，`ee/` 目录企业功能付费。**当出现"多步骤可持久化工作流"需求**（如定时自动复盘流水线、人机确认节点、跨会话记忆）时，在 AI SDK 之上叠加其 workflow/agent 层，二者官方口径互补。出处：<https://github.com/mastra-ai/mastra>

### 2.5 其他

- **LlamaIndex.TS**：已于 2026-04-30 归档废弃，直接排除。<https://github.com/run-llama/LlamaIndexTS>
- **Dify / Coze 低代码平台**：适合非开发者快速搭内部工具；对已有 TS 代码库重构价值低（逻辑搬进平台，失去版本控制与类型系统）。

## 3. 协议与生态

### 3.1 MCP（Model Context Protocol）—— 建议借力

Anthropic 发起的开放标准（"AI 应用的 USB-C"），spec 已迭代到 2026-07-28，Claude、ChatGPT、VS Code、Cursor、Codex、Gemini CLI、Cline 等广泛支持。**对个人项目最实际的收益**：把拾光的系统能力（今日概览查询、发动态记账、周报复盘）封装成一个 MCP server，即可在所有主流编码工具里当工具直接调用——等于给自己的系统开一个 AI 原生的开放接口。A2A（agent 间互联协议）个人项目暂无刚需。出处：<https://modelcontextprotocol.io/>

### 3.2 AGENTS.md 约定 —— 零成本必做

已成为跨工具开放标准（Linux 基金会托管，Codex/Cursor/Gemini CLI 等都读），monorepo 支持嵌套就近生效。本仓库由"单人 + AI 编码代理协作"开发（git log 佐证），在根目录与各 package 写清构建/测试命令与代码规范，配合代理的 plan mode 形成**测试闭环**，是提升后续所有开发质量/安全性的最低成本手段。出处：<https://agents.md>

## 4. Agentic coding 工具一览（背景参考）

| 工具 | 定位（1-2 句） |
|---|---|
| Claude Code | Anthropic 旗舰终端/IDE 编码代理，plan mode、子代理、hooks、CLAUDE.md 记忆；多日重构工作流最强 |
| OpenAI Codex CLI | 开源（Rust），CLI/IDE/云端多形态，原生 AGENTS.md，沙箱执行 |
| Cursor | AI 原生 IDE/agent，云端并行 agent 机队 + CLI，订阅制 |
| Gemini CLI | 开源，1M 上下文，个人账号免费额度大，支持 GEMINI.md/AGENTS.md |
| Cline / Roo Code | 开源 VS Code 代理扩展，Plan-Act 双模式、checkpoint 回滚、自带 API key |
| Aider | 终端结对编程，git 自动提交、仓库地图、模型覆盖最广 |
| OpenHands | 自托管 Agent Canvas，统一编排多个编码代理 |
| SWE-agent | 研究型自主修 issue 代理，已仅维护模式（被 mini-swe-agent 取代） |

**工作流最佳实践**（对本仓库可直接采用）：① 根目录 AGENTS.md 写明命令与规范；② spec-driven development（先规格后实现，即本仓库 01→02→03 文档流程的工程化版本）；③ plan mode 先行，人审后再执行；④ 测试命令写进约定，代理自动跑测试修复失败。

## 5. 选型结论

| 决策 | 结论 | 理由 |
|---|---|---|
| LLM 传输层 | **引入 Vercel AI SDK**，替换 `glm.ts` / `jev.ts` 手写 HTTP | 替换传输层而非重写架构；统一 GLM/Jev 双供应商抽象；流式/结构化输出/重试由官方接管；社区最大问题好查 |
| ASR | `transcribeAudio` **保留自研**（GLM-ASR 为厂商专属接口，SDK 不覆盖），仅补重试/超时/审计 | 见 02 §7.6 |
| 工作流编排 | 暂不引入 Mastra；出现持久化工作流需求时再叠加 | 当前识别/复盘管线用代码编排已够 |
| MCP | 4-H 批次（可选）：新增 MCP server 暴露拾光查询/记账能力 | 一次封装、所有主流编码工具可用 |
| 工程约定 | 根目录 + 各 package 嵌套 **AGENTS.md**，纳入 4-A 批次 | 零成本提升 AI 协作开发质量 |
| 迁移成本 | 按模块渐进替换，对话/总结链路各约半天~一天 | chat↔generateText、extractJson↔generateObject 一一对应；重问与降级链保留在应用层 |
