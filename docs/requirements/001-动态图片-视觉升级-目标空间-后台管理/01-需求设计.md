## 1. 背景与定位

「拾光」是自助研发的**个人成长经营 AI 系统**，主线为 **时间 · 目标 · 人际 · 财务**。当前处于 Phase 4（复盘 v3 已上线，目标主线与上线收尾进行中）。本批四个需求：

- **R3 目标空间**是四主线中「目标」主线的正式落地——此前系统只记录"发生了什么"（动态）和"要做什么"（待办），缺少"这一切服务于什么"的顶层容器；
- **R1 图片上传**补齐动态记录的素材维度（饭照、截图、成就瞬间），现状动态为纯文本；
- **R2 视觉升级**把全站标签/emoji 统一到待办看板（todo-board）改造后的视觉范式，消除风格割裂；
- **R4 后台管理**建立运营基建：AI prompt 可在线调优（当前全部硬编码）、管理功能集中（当前管理员功能散落、管理员身份硬编码）。

## 3. R1 动态图片/拍照上传

### 3.1 现状与痛点

- 动态唯一创建入口 `POST /api/parse` 只收纯文本 `{ text }`；`entries` 表仅有 `audio_url` 预留列（从未写入），无任何图片表、无文件上传基础设施。
- 全仓库无图片展示代码（无 `<img>`/`next/image`/RN `Image`）。
- Web 发布面板（publish-sheet）与桌面输入区均为纯 textarea；Expo App 无 `expo-image-picker` 依赖。
- 唯一的上传先例是语音 ASR（formData + 15MB 上限 + 魔数嗅探），可复用其模式。

**痛点**：生活中大量值得记录的信息载体是图片（餐食、账单截图、健身成果、旅行瞬间），纯文本动态表达力不足，也影响后续"记录 → 复盘"的完整性。

### 3.2 用户故事

- 作为用户，我在记录"和王智聪吃饭"时想附一张饭局照片，让这条动态更完整。
- 作为用户，我在手机上想直接拍一张照作为动态素材，不用先拍好再去相册找。
- 作为用户，我想在动态流里直观看到每条动态的配图，点开可大图浏览。

### 3.3 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-1.1 | 上传入口 | 三端发布入口均增加图片按钮：桌面输入区、移动端发布面板（PublishSheet）、Expo App 输入面板；支持**相册多选**与**拍照**（移动端提供"拍照"独立入口，`capture` 调起相机） |
| FR-1.2 | 数量与规格 | 单条动态 ≤ **9** 张；上传前**客户端压缩**（长边 ≤1920px、JPEG 质量 0.85，目标单张 ≤2MB）；原图接受 jpeg/png/webp/gif |
| FR-1.3 | 发布时序 | 文字先发布（复用现有秒回），图片随后**并行上传**；单张失败不阻塞文字动态与其他图片，失败可重试 |
| FR-1.4 | 展示 | 动态卡片内九宫格布局（1 张大图 / 2-3 张横排 / 4-9 张网格）；点击进入全屏预览（左右切换）；懒加载，加载失败显示占位 |
| FR-1.5 | 编辑与删除 | 删除动态时图片一并删除；编辑原文不影响图片；支持在动态上删除单张图片 |
| FR-1.6 | 访问控制 | 图片 URL 路径不可枚举（uuid key）；访问需登录态且**仅本人可见**（与全站数据归属一致） |
| FR-1.7 | 服务端校验 | 魔数白名单校验（防改后缀）、单张 ≤5MB（压缩后兜底）、单条 ≤9 张（含已上传）、登录态校验 |

### 3.4 边界与异常

- 网络中断：上传失败的图片在发布面板保留缩略图与"重试"按钮。
- 上传中关闭页面：文字动态已发布不回滚，图片丢失可接受（个人系统，提示即可）。
- 不支持的格式（如 heic 直接拖入 web）：前端过滤 + 后端魔数拒绝，提示"仅支持 jpg/png/webp/gif"。
- iPhone HEIC：Expo 端 `expo-image-picker` 配置转 JPEG 后上传。
- 历史动态无图：feed 展示逻辑需兼容 `images` 为空。

### 3.5 非功能需求

- 图片上传不阻塞文字发布（体验优先）。
- 存储层 key 抽象（`storage_key`），未来可平滑迁移对象存储（COS/OSS）。
- 生产上传目录必须独立于发布原子交换目录，避免发版丢失文件（详见 02 设计 §3.2）。

### 3.6 验收标准

- [ ] Web 桌面输入区、Web 移动发布面板、Expo App 均可选图（多选 ≤9）发布带图动态
- [ ] 移动端（PWA + Expo）可拍照上传
- [ ] 上传前自动压缩，单张上传体积 ≤2MB 量级（1920px 长边）
- [ ] 动态卡片九宫格展示、点击全屏预览、可左右切换
- [ ] 删除动态后图片行与磁盘文件均被清理
- [ ] 未登录访问图片 URL 返回 401；他人（无归属权）访问返回 403/404
- [ ] 伪造后缀（如 .jpg 实为 exe）被魔数校验拒绝
- [ ] 服务器重新发布（双 tar 交换）后历史图片仍可访问

## 4. R2 全站标签/emoji 视觉升级

### 4.1 现状与痛点

待办看板（todo-board）2026-09 改造后建立了成熟视觉范式：**渐变激活 chip、语义色 tinted 徽标、hover 操作组、glass 卡片**。但全站其余页面 emoji/标签形态各异：

| 形态 | 例子 | 位置 |
|---|---|---|
| 裸 emoji 排文本 | 📋 待办 / 💰 金额 / 🍽 饮食 / 💚 要点 / 💡 建议 | moment-feed 产物行、calendar 复盘卡 |
| 灰底小 chip（无语义色） | 📋 话术 / 🕒 时间 / ✨ AI / 📝 手动 | moment-feed 意图标签 |
| emoji + 渐变激活 pill | 📅 日历 / TODO / 🏷 分类；📋 列表 / 🕸 图谱 | schedule、contacts |
| 彩色文字行 | 💚 喜欢 / ⚠️ 忌讳 / 📌 记住 | contacts/[id] 详情 |
| 有语义色但各自为政 | 收/支徽章、⭐重要/☀️今日 | finance、todo 系（达标，作为基准） |

**痛点**：同一层级的语义标签在不同页面视觉重量、圆角、底色、字号不一致，整体质感与 todo-board 脱节。

### 4.2 目标视觉语言（对齐 todo-board 范式）

1. **展示型标签**：emoji 一律装入 **tinted chip**——语义色 15%~20% 透明底 + 同色系文字，`rounded-lg` 小圆角、`text-[11px]` 级字号、medium 字重；**同一概念全站同色**（映射表见 02 设计 §4.2）。
2. **交互型 chip**（筛选/切换/视图）：沿用 todo-board 的渐变激活态（sky→indigo 渐变 + 白字 + 光晕阴影），未激活为 ghost 形态。
3. **不引入第三方图标库**，继续以 emoji 为图标载体，只做容器化包装。
4. 纯样式与组件封装改造，**不动数据结构与接口**。

### 4.3 改造范围

| 页面/组件 | 改造点 |
|---|---|
| moment-feed（动态流） | 意图标签、产物行标签（待办/金额/人物/饮食）、语音/识别中/待确认状态条 → tinted chip；心情行维持 moodTone 上色体系 |
| schedule（日程页） | 三个 tab 统一为公共 FilterChip（渐变激活） |
| contacts 列表 + 详情 | 分组筛选 chip（GROUP_COLOR→tone 映射）、详情页标签行（生日/纪念日/往来/收送/画像）chip 化 |
| finance（财务页） | 章节标题 emoji、账户 icon、分类展示 → tinted chip 化（收/支徽章已达标） |
| calendar 复盘卡 ×4 | 💚 要点 / 💡 建议 bullets → 统一 chip/圆点体系 |
| reminders、bill-import、day-donut、day-timeline | 提醒横幅条目 icon、账单来源、活动 icon（DB emoji）统一包装 |
| profile、publish-sheet、entry-menu、login 等 | 装饰性 emoji 择要 chip 化（低优先） |
| todo-board / today-todos | **基准不动**（仅抽取公共组件供复用；首页今日区随 R3 改造为行动清单） |

### 4.4 约束与验收

- 深色/浅色双主题逐页检查。
- 触屏设备（`hover:none`）下操作入口不依赖 hover（沿用现有 row-actions 常显机制）。
- DB 中无 icon 的活动/分类回退 emoji（📌 等）保持可用。

- [ ] 全站展示型 emoji 标签均为 tinted chip，无裸排残留（装饰文案除外，清单见 02 设计）
- [ ] 同一概念全站同色（对照映射表抽查）
- [ ] 交互 chip 激活态与 todo-board 一致（渐变 + 计数徽标）
- [ ] 深浅主题、移动端 PWA 布局无破版

## 5. R3 目标空间模块（P0）

### 5.1 概念定义

| 概念 | 定义 |
|---|---|
| **目标空间** | 一个宏大目标的容器，建议持续 **≥1 年**（如"考研上岸""副业月入过万""完成全马"）。拥有名称、图标、颜色、描述、起止时间；可归档 |
| **待办（todo）** | 服务于空间的阶段性任务（现有 todos 表，挂 `space_id`） |
| **行动（action）** | **个人最小执行单元**（原"子任务"更名）：一次专注（25 分钟~2 小时）内可完成、可验证。**行动之下不再有子行动**（只有一层）。行动可以：带**描述**（note）、设**每日重复**、记录**已完成次数**；行动在待办下**有序排列** |

> v1.1 澄清：取消 v1.0 中"行动再拆解出子行动（最多 3 个）"的分层设计——行动即最小单元，"把行动拆细"的产物是**同级的更小行动**，插入到原行动之后（见 FR-3.6），不产生层级。

关系：`空间 1—N 待办`；`空间 1—N 动态`（动态可归属空间，也可无归属）；`待办 1—N 行动`（仅一层、有序）。

**记录日口径**：每日重复的恢复以 **06:00 为记录日界**——凌晨 00:00–05:59 仍视为前一记录日（与系统既有的"凌晨回填算前一天"口径一致）；06:00 日切后，重复行动恢复为未完成。

### 5.2 用户故事

- 作为用户，我为"今年上岸"建一个目标空间，把这一年相关的动态和待办都聚在它下面，随时看到自己为目标投入了什么。
- 作为用户，我发动态时不想手动选空间——系统识别出这条动态和某个空间相关就自动归类，不确定的我自己改。
- 作为用户，我在动态页可以按空间切换视角：只看"上岸"相关的动态，或看全部。
- 作为用户，我每天打开首页就能看到**今日行动清单**——来自各待办拆出的行动，一件件勾掉，清单里只有行动，不被待办混杂。
- 作为用户，我给"读书 30 分钟"设了每日重复：今天做完勾掉，明天 6 点后它自动回到未完成，并累积完成次数，让我看到自己坚持了多少天次。
- 作为用户，我对着"准备复试"这条待办没有头绪时，点一下 AI 拆解，它给我列出一串可执行的行动，我逐个勾掉。
- 作为用户，某个行动还是太大时，我让它再拆成几步更小的行动——**新行动紧跟在原行动后面插入**，不打乱我清单里其他行动的顺序。

### 5.3 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-3.1 | 空间管理 | 创建/编辑/归档/恢复空间：名称（≤40 字）、emoji 图标、颜色、描述、开始/目标日期；新增「目标」主导航入口，空间列表页展示进度概览 |
| FR-3.2 | 动态页空间切换 | 动态流顶部横滑 chip：**全部 / 未归属 / 各 active 空间**；样式对齐 todo-board 渐变激活态 |
| FR-3.3 | 动态归属 | ① **AI 自动归属**：发布识别完成后，若存在 active 空间，轻量分类调用判断归属，置信 ≥0.7 自动写入；② **手动**：动态卡片菜单可选择/切换/移除所属空间 |
| FR-3.4 | 待办关联空间 | 创建待办时可选空间；AI 从动态识别出的待办**继承动态的空间**；待办行显示空间徽标、可修改 |
| FR-3.5 | 行动管理 | 待办下手动添加行动（有序，支持插入位置）；行动可编辑**描述**（note，≤1000 字）；**行动不可再有子行动**（服务端沿用"父必须顶层"校验）；行动可勾选完成 |
| FR-3.6 | AI 拆解（插入式） | ① **拆解待办**：一键生成 **≤10** 个行动；已有行动时提示"追加到末尾 / 重新生成（清空未完成）"；② **拆解行动**：对某行动一键细化出 **≤3** 个更小的**同级行动**，**插入到该行动之后**（原行动保留，后续行动顺延）；生成结果可删改 |
| FR-3.7 | 空间详情页 | 空间信息（可编辑）+ 关联待办列表（含行动列表、AI 拆解入口）+ 关联动态流 + 进度概览（待办完成率、行动完成率） |
| FR-3.8 | 首页今日行动清单 | 首页原"今日待办"区改为**「今日行动清单」**，只展示**行动级**条目：① 设了每日重复的行动（每天出现）；② 父待办标记今日或今日到期的行动。不展示顶层待办（顶层待办仍在 /schedule 看板）。行动行显示父待办名（小字上下文）、🔁 重复徽标、已完成次数 |
| FR-3.9 | 每日重复与已完成次数 | 行动可设**每日重复**（🔁 开关）；完成时**已完成次数 +1**（同一记录日内反复勾选不重复计数）；**06:00 日切后**已完成的重复行动自动恢复为未完成（可再次完成并计数）；次数在行动行展示（如 ×12） |

### 5.4 边界与异常

- active 空间数量软上限 **20 个**：超出提示先归档（控制 AI 分类 prompt 长度与认知负担）。
- AI 归属置信 <0.7 不写入；无 active 空间时跳过分类调用；分类失败静默，不影响动态识别主流程。
- AI 拆解消耗 AI 识别额度（与 parse 同池，管理员不限）；LLM 输出不符合契约自动重问一次（复用现有 repair 机制），仍失败则提示稍后再试。
- 删除空间需二次确认，动态/待办的 `space_id` 置空，**不删任何业务数据**；归档空间不出现在切换条（可展开查看），AI 不再归类到归档空间。
- 行动层级：**仅一层**——给行动添加子任务被服务端拒绝；`is_important`/`today` 标记仍仅限顶层待办（沿用现有约束）。
- 每日重复边界：
  - 00:00–05:59 完成仍计入前一记录日（与全局凌晨回填口径一致），不触发恢复；
  - 同一记录日内 完成→取消→再完成，次数只 +1；取消勾选不回退已记录次数；
  - 删除父待办级联删除其行动（含重复行动）——删除确认文案提示；
  - 重复行动不受空间归档影响（首页清单照常出现）。
- 插入式拆解：拆解结果插入后可逐条删改；「重新生成」仅清空**未完成**行动，已完成行动与次数保留。
- /schedule 看板的 ☀️今日视图保持顶层待办粒度不变（与首页行动清单是两个视图）。

### 5.5 验收标准

## 6. R4 后台管理系统

### 6.1 现状与痛点

- 管理员身份 = 硬编码 UUID（`DEV_USER_ID`），散落 **7 处**判断（me/invites/billing/users/tokens/quota/review-quota），无 role 字段。
- 邀请管理面板挂在 `/profile` 个人设置页，与用户列表、Token 消耗、套餐管理分散。
- **全部 AI prompt 硬编码在代码里**（packages/ai 8 个 + 复盘 4 个 + 画像合并 1 个），调优必须改代码发版，无版本管理。

### 6.2 用户故事

- 作为超级管理员，我想在网页上直接调整某个 AI prompt 并立即生效，不用改代码、走发版。
- 作为超级管理员，prompt 改坏了能一键回滚到之前的版本，或一键切回代码默认值。
- 作为超级管理员，我写 prompt 没把握时，可以让 **AI 协助优化**出一版建议稿，对比当前内容后决定采纳与否，**采纳后仍由我手动保存**，AI 不会直接改线上 prompt。
- 作为超级管理员，我在一个后台里完成：生成邀请码、看被邀请人及其 Token 消耗、管理用户套餐。

### 6.3 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| FR-4.1 | 权限模型 | `profiles.role`（`user`/`admin`）；存量开发账号迁移为 admin；所有管理员接口统一走 `requireAdmin`；`/admin` 页面非 admin 显示 403 态；`/api/admin/*` 硬校验 role |
| FR-4.2 | AI 管理模块 | ① prompt 清单（key、用途、启用态、是否被 DB 覆盖、最近更新）；② 在线编辑保存，**保存即生效**（进程内缓存 ≤60s，保存后主动失效）；③ 每次保存留版本快照，支持任意版本回滚与"恢复代码默认"；④ 启用开关（关闭=用代码默认值）；⑤ **AI 协助优化**：编辑器旁「✨ AI 优化」按钮（可附一句优化意图），AI 返回优化建议稿，前端**并排对比**（当前 / 建议），「采纳」仅把建议填入编辑器（未保存状态），「放弃」丢弃；**保存仍需手动确认**，优化建议本身不落库、不产生版本；⑥ 试运行（贴一段话术看解析输出，二期可选） |
| FR-4.3 | 营销管理模块 | 迁移邀请码生成/列表/状态（原 InvitesPanel）；被邀请用户列表与 Token 消耗统计；用户列表与套餐管理（原 /profile 管理员区块） |
| FR-4.4 | 信息架构 | `/admin` 页含「AI 管理」「营销管理」两个模块；`/profile` 移除管理员区块、替换为后台入口卡；`/invites` 旧跳转改指 `/admin` |

### 6.4 边界与异常

- prompt 保存校验：非空、≤50000 字；覆盖后 `packages/ai` 的代码默认值始终保留为回退底座。
- AI 优化调用本身消耗 token（管理员不限额度），结果仅供对比参考；优化失败提示稍后再试，不影响编辑器现有内容。
- 静态导出下页面代码可被查看，无敏感信息；真正的门禁在 API 层 role 校验。
- prompt 编辑失误的兜底：版本回滚 + 启用开关秒切默认。
- 被邀请人 Token 统计、邀请码校验逻辑（注册强制邀请码）不变，仅管理界面迁移。

### 6.5 验收标准

- [ ] admin 账号可访问 `/admin`，普通账号页面 403 态 + `/api/admin/*` 全部 403
- [ ] 修改任一 prompt 保存后，≤60s 内线上识别行为变化（无需重启/发版）
- [ ] 版本历史可回滚；关闭启用开关后立即回退代码默认行为
- [ ] 「AI 优化」返回建议稿并可对比；「采纳」后仅填入编辑器、**不自动保存**；直接关闭不落库、无版本产生；优化调用有审计记录
- [ ] 邀请码生成/列表/状态在 `/admin` 可用，注册流程不受影响
- [ ] 用户列表、套餐修改、Token 消耗统计在 `/admin` 可用
- [ ] `/profile` 无管理员功能残留，仅 admin 见后台入口
- [ ] `/invites` 跳转到 `/admin`
