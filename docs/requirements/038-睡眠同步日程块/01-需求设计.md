# 038 · 睡眠数据自动同步日程块 —— 需求设计

> 批次性质：打通「健身-睡眠」与「日程-时间块」两个域。此前 `fitness_sleep_logs` 只存「北京日期 + 总时长（+感受/得分）」，与 `time_blocks` 完全不通：用户记了睡眠，日历/当日结构/统计/复盘里却看不到睡眠时间分布。本需求后，**保存或打卡睡眠即自动在该日日程生成「😴 睡眠」跨天时间块**，日历四视图（日/周/月/年）、当日结构圆环、时长统计与复盘管线自动可见——同步产物即普通时间块，展示端零改动。

## 一、背景与痛点

- 睡眠是每天占比最长的时间段（默认 8h），但只以「数字」存在于健身页；日程视角的时间全景缺了最大的一块。
- 复盘/小结按时间块取数，睡眠缺席导致「一天时间去哪了」永远对不上。
- 手动在日历补录睡眠段（ round 17 已支持跨天块）需要用户手动换算入睡时刻，重复劳动且与睡眠记录无关联。

## 二、需求描述

### FR-1 自动生成日程睡眠段

保存睡眠（健身页睡眠卡手动保存）或打卡带睡眠时长（计划打卡 `sleepHours`、独立补录 `POST /api/fitness/logs`）后，系统自动在该日日程生成一个「😴 睡眠」时间块：

- 时间锚点 = **起床 07:00（北京）**，块区间 = `[log_date 07:00 − 时长, log_date 07:00]`。
  - 例：log_date=2026-10-23、8h → 块为 10-22 23:00 → 10-23 07:00（跨天块，两个日视图各自显示所属段；日小结/统计按天钳制分摊，既有口径）。
  - 选起床锚点的理由：`log_date` 语义本就是「X 日醒来的昨晚睡眠」，起床时刻恒定、入睡随时长浮动。
- 块属性：`activity_id='sleep'`（😴 预设分类）、`title='睡眠'`、`time_mode='manual'`、`source='manual'`（不扩 source 约束，同步块靠 `sleep_log_id` 非空识别）。

### FR-2 重复保存幂等（替换式）

同日重录（如先记 8h 再改 6h）→ 旧同步块被替换，恒至多 1 块；区间随新时长移动（6h → 01:00–07:00）。

### FR-3 冲突跳过 + 告知

- 与既有日程重叠（含用户手动补录过的睡眠段、历史导入的块）时**不写入**，返回服务端冲突文案（复用 `overlapError`「一个时刻只能做一件事」口径）。
- 冲突时**保留原同步块不删**（先预检再删旧）：改短时长撞上别的日程时，旧段不丢。
- web 手动保存路径 toast 展示「😴 睡眠已记录；日程同步跳过：<原因>」；打卡/补录路径静默降级（睡眠数据照常落库）。
- 睡眠数据本身无论冲突与否恒保存成功。

### FR-4 0 小时 = 撤销

时长改为 0 → 仅删除对应同步块，不建新块；睡眠记录本身保留（`sleep_h_x10=0`）。

### FR-5 用户编辑即解绑

- 日历上**编辑**同步块（改时间/标题/类别）→ `sleep_log_id` 置空：用户的修改保留为普通块；该日再次保存睡眠时生成**独立新块**（不复活、不复用）。
- **删除**同步块同理：删除不复活；再次保存睡眠生成新块。

### FR-6 存量回填

上线迁移内一次性幂等回填：全部历史睡眠记录（时长>0、尚无对应块）按同一 07:00 锚点生成跨天块；与既有日程重叠者跳过（与运行时冲突策略同口径）；用户缺「睡眠」预设分类者跳过。

## 三、明确不做

- 不做入睡/起床真实时刻录入（数据模型无此字段，不扩需求）。
- 不改小程序端 UI（同步在服务端，小程序日程页自动可见）。
- 不提供同步开关（保存即同步；FR-5 编辑解绑已覆盖「不想同步」场景）。
- 缺「睡眠」分类的用户（理论上不存在：注册即播种、预设不可删）优雅跳过同步，不阻塞睡眠保存与打卡事务。
