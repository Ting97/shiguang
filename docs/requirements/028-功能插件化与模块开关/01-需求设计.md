# 028 · 功能插件化与模块开关 · 需求设计

> 状态：草稿 · 2026-10-16 · 前置：003（模块授权）、018（运动空间）· 可行性论证见 [00-可行性方案](00-可行性方案.md)

## 背景与目标

用户要求（2026-10-16）：

> 「所有功能都可以插件化模块化的，可以支持在后台管理可控的开关，根据每个用户的不同要求可以开关，同时用户可以在【我的】界面里开关按钮。」

现状只满足了一小角：REQ-003 起财务三个子模块（debt/trade_review/trading）支持管理员按用户授权，用户侧表现为财务页 tab 显隐，但模块清单硬编码、无全局开关层、无用户自选层、导航/首页/AI 入口对模块无感知。

本批把该机制**泛化为全站模块体系**：

1. 域级 + 子模块两级模块注册表，作为模块清单的单一事实源；
2. 三层开关模型：管理员全局开关 → 管理员按用户强制/开关可见性 → 用户自选；
3. 后台管理端与用户【我的】页面两端开关 UI；
4. 关闭 = 隐藏入口 + 直连兜底 + API 拦截，数据保留。

## 边界与非目标

- **不做运行时动态装载/热插拔**：模块代码仍随构建发布，「插件化」指注册表化 + 可开关（可见性/可用性），非微内核插件框架（论证见 00）。
- **不做按模块数据删除**：关闭只影响可见性与 API 可用性，数据保留，重开即恢复。
- **不改 Android/native 壳**：壳加载同一 web 产物自动生效，无需重出 APK。
- **`timeline`（动态/首页）为 core 模块**：不允许任何层关闭，避免首页本身消失导致全站空转；注册表以 `core` 标记支持未来调整。
- 聚合端点（today/feed）与导出（/api/export）不做 403 门禁（前者按模块过滤内容，后者保留全量导出以便用户取回关闭模块的数据）。
- 小程序（apps/miniapp）默认不动（沿用既有暂停约定），注册表设计上不排除未来接入。

## 决策记录

1. **泛化 031 机制而非新建插件框架**：静态导出 + monorepo 三端形态下，运行时插件框架不可行也不必要；现有「flag 表→withModule→me 下发→前端过滤→admin 矩阵」五环全通。
2. **粒度=域级+子模块两级**（用户拍板）：域整体开关满足大多数场景；高频独立开关的子功能（健身/睡眠/交易等）单独成模块。不做面板/按钮级细粒度（配置爆炸）。
3. **默认策略分两类**（用户拍板）：基础模块默认开、用户可自行关闭；高级模块（trading/debt/trade_review）沿用现状默认关 + 管理员开通。每模块注册表标记 `defaultOn`。
4. **开关可见性是按用户能力**（用户拍板）：管理员除强制开/关外，还控制每个用户【我的】里展示哪些开关项（三态：跟随全局 user_toggleable / 强制可见 / 强制隐藏）。
5. **关闭语义 = 隐藏入口 + API 403 + 数据保留**（用户拍板）：复用 ModuleLocked 与 withModule，安全边界在后端。
6. **注册表放 packages/shared**：web 静态导出需要构建期模块清单（名称/层级/导航项），运行时只下发状态；api 从 shared import 保证两端同源。
7. **三层状态分三张表**：全局层/按用户层/用户自选层写主体与语义不同（管理员/管理员/用户），合表会混审计与并发写；旧 user_module_grants 搬迁后保留停写（迁移只增不改）。
8. **聚合端点过滤而非拦截**：首页必须可渲染，today/feed 按模块过滤内容，避免「关一个域炸整个首页」。
