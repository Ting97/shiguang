# 028 · 功能插件化与模块开关 · 可行性方案

> 状态：草稿 · 2026-10-16 · 后续：01-需求设计 / 02-开发设计

## 一、需求原话与目标

> 「所有功能都可以插件化模块化的，可以支持在后台管理可控的开关，根据每个用户的不同要求可以开关，同时用户可以在【我的】界面里开关按钮。」

拆解为四层能力：

1. **模块化**：功能以「模块」为单元纳入统一注册表（域级 + 子模块两级），而非散落在导航、路由、首页的硬编码里。
2. **后台可控（全局）**：管理员可对每个模块做全局开关（下线/灰度）。
3. **后台可控（按用户）**：管理员可按用户强制开/关某模块，并控制该用户在【我的】里能看到哪些开关项。
4. **用户自选**：用户在【我的】→ 功能管理里，对被允许的模块自行开关，即时生效。

## 二、现状盘点：已有一条跑通的「按用户模块开关」链路

REQ-003（迁移 031）已为财务三个子模块落地完整链路，**本批是泛化而非新建**：

| 环节 | 现状文件 | 现状能力 | 缺口 |
| --- | --- | --- | --- |
| 模块清单 | `apps/api/src/server/platform/modules.ts` `MODULES=["debt","trade_review","trading"]` | 3 个 key，TS 常量 | 无元数据（名称/默认态/路由归属），无域级模块 |
| DB 存储 | `user_module_grants`（迁移 031，CHECK 约束 031/037 两扩） | (user_id, module) 授权=开 | 仅「授权开」单态；无全局层、无用户自选层 |
| API 门禁 | `platform/http/route.ts` `withModule/withModuleParams` HOF，覆盖 18 个财务路由 | 三态门禁（401/403/过） | 仅 3 模块路由有包裹；逐文件手工包裹易漏 |
| 会话下发 | `identity/service.ts` `me()` 返回 `modules: string[]` | 前端可读有效模块 | 语义=「管理员授权的财务模块」，非全量有效态 |
| 前端可见性 | `apps/web/src/components/finance-tabs.tsx`（唯一按 modules 裁剪的导航） | tab 显隐 | `nav.tsx` LINKS 硬编码 5 项；首页/AI 入口无感知 |
| 直连兜底 | `apps/web/src/components/module-locked.tsx`（🔒 未开通页） | 3 个财务子页使用 | 未推广到其他域 |
| 后台管理 | `/api/admin/grants` + `apps/web/src/app/admin/page.tsx` 的 `admin-marketing-panel.tsx` 授权矩阵 | 点按授权/撤销，即时生效 | 仅「开/无」两态；无全局开关、无开关可见性控制 |

其他可复用资产：

- **全局开关先例**：`app_config`（迁移 030）+ `ai/ai-mode.ts` 的「DB 覆盖 + env 兜底 + 60s 进程缓存 + 写时主动失效」模式。
- **注册表先例**：`chat/tools.ts` 的 `TOOL_DOMAIN`（工具→域映射 + `toolsForScope` 过滤）；`fitness_modules`（DB 数据驱动目录 + `is_active`）。
- **多用户底座**：`profiles.role('user'|'admin')`（迁移 024）、所有业务表按 `user_id` 隔离、`audit_logs` 审计表。

## 三、方案选型

| | 方案 A：泛化现有 modules 机制（推荐） | 方案 B：运行时插件框架（微内核/动态装载） |
| --- | --- | --- |
| 思路 | 模块代码仍随包构建发布，把「模块清单+三层开关状态」抽象为注册表与状态表，开关控制的是**可见性与可用性** | 引入插件生命周期（install/activate/deactivate）、独立打包、运行时装载卸载 |
| 契合度 | 完全复用 031 链路与 admin UI；静态导出（`output: export`）下前端构建期就需要模块清单，注册表放 shared 天然满足 | 与 Next.js 静态导出 + npm workspaces monorepo 冲突：静态产物无法运行时装载；三端（web/android/native）需各自插件运行时 |
| 成本 | 三张状态表 + 一个注册表 + 门禁补齐 + 两端 UI | 近乎重写应用骨架 |
| 结论 | **采用** | 过度设计，不做（见非目标） |

**可行性结论：高。** 核心链路（按用户 flag 表 → API 门禁 HOF → me 下发 → 前端过滤 → admin UI）五环全部已存在且在生产运行，改造量集中在「扩容」：模块清单从 3 个 key 扩到两级全量、状态从单层扩到三层、门禁与前端感知从财务 tab 扩到导航/首页/AI/空间。

## 四、风险清单与对策

| # | 风险 | 对策 |
| --- | --- | --- |
| R1 | 门禁覆盖遗漏：约 150 个 route.ts 中受控路由需逐个包 `withModule`，新路由易漏 | 注册表声明 `apiPrefixes`，routes-smoke 测试断言「受控前缀必带门禁」；评审清单核对 `apps/api/src/app/api/` 目录 |
| R2 | 性能放大：`getModuleUser` 每请求实时查库，泛化到全模块/全路由后 DB QPS 上升 | 判定收敛为一次 `resolveUserModules(userId)`（三表一次查），进程内 TTL 缓存 + 写路径主动失效（复用 ai-mode 模式；当前 systemd 单实例成立） |
| R3 | 静态导出约束：web 是纯静态产物，模块清单无法运行时下发 | 注册表放 `packages/shared`（纯数据、构建期 import），运行时只下发每用户**状态**（搭 `me()` 顺风车） |
| R4 | 首页跨域耦合：`app/home/use-home-data.ts` 一次拉 today/feed/reminders/spaces，识别产物卡片覆盖全部域 | 聚合端点（/api/today、/api/feed）不加 403 门禁，改为按模块**过滤返回内容**；前端区块按 `user.modules` 条件渲染 |
| R5 | platform↔identity 浅环：`modules.ts` 已反向 import `identity/auth` | 重写时维持现状依赖方向（经 index 门面），不新增反向依赖 |
| R6 | `me().modules` 语义变化（从「财务授权清单」变为「全量有效开启清单」） | 字段名与类型不变；现有唯一消费方 `finance-tabs.tsx` 的 `includes('debt')` 判断天然兼容；android/native 壳加载同一 web 产物无感 |
| R7 | admin 矩阵 UI 复杂度：用户×模块矩阵叠加三态+可见性 | 单元格点击循环「跟随→强制开→强制关」，可见性作为单元格内独立小开关；沿用 marketing-panel 交互骨架 |
| R8 | 存量数据：`user_module_grants` 现有授权必须无感 | 迁移 063 搬迁至新表（on conflict do nothing），旧表保留停写（迁移只增不改） |
| R9 | 全关空态：用户把可关模块全部关闭后首页空转 | `timeline`（动态）标记 core 不可关；空态引导卡指向【我的】→ 功能管理 |
| R10 | Edge middleware 不能查库：`src/middleware.ts` 在 Edge runtime 无法做模块门禁 | 门禁保持在 route handler 层（withModule），middleware 不参与模块判定 |

## 五、分期实施（详见 02-开发设计）

- **Phase 1 基础设施 + 试点**：shared 注册表、迁移 063（三张状态表 + 存量搬迁）、三层有效态计算与缓存、`me()` 扩展、用户 `PATCH /api/auth/module-prefs`、admin「模块」tab 与授权矩阵三态化、`nav.tsx` 注册表化、【我的】功能管理区；试点接入 finance 域（含既有 3 子模块）+ people + fitness。
- **Phase 2 全域接入**：time/goal/ai/insight/sleep 等剩余模块路由门禁、ModuleLocked 推广、首页聚合与 AI 助手 scope 联动、空间训练 tab 开关联动、旧重定向页兼容。
- **Phase 3 打磨**：开关变更审计（audit_logs）、空态与引导、Android 壳真机验证、（可选）按套餐 plan 联动默认态。
