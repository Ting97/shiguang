# 14 · 三端适配与商业化方案对比（安卓 / iOS / Web）

> 背景：Web 已上线（Next.js 15 + PostgreSQL + GLM），安卓 WebView 壳已交付（`feat/android-apk`）。本文面向**三端 + 商业化**目标，对比主流方案并给推荐。注：`docs/03` 技术方案最初就规划了 **Next.js + Expo** 组合，本文方案 B 即原始路线的回归。

## 方案总览

| | A. Capacitor 正式化壳 | B. Expo(RN) + Next.js 双客户端 | C. Flutter 全端 | D. 微信小程序（补充渠道） |
|---|---|---|---|---|
| 一句话 | Web 单代码库打三端包，插件补原生 | 移动端原生重写，Web 不动，共享逻辑层 | 一套 Dart 代码含 Web | 微信生态获客 + 支付 |
| 移动端 UX | WebView 级（同现状壳） | ⭐原生级（四方案最佳） | 原生级 | 小程序框架级 |
| Web 端 UX | 完全保留现状 | 完全保留现状 | 三方案最弱（首包大/canvas 渲染） | H5 版较弱 |
| 代码复用 | ~100%（UI 全复用） | 逻辑/类型/设计 tokens 复用，UI 双写 | 100% 但需全重写 | Taro 复用 React 语法 |
| 一次性成本 | 2~3 周（认证/API 改造为主） | 4~8 周 | 10 周+（含废弃现有 Web） | 2~4 周 |
| 持续成本 | 极低 | 新功能双端 UI（逻辑共享后 +30~40%） | 低（单库）但换生态 | 中（多一套渠道代码） |
| 迭代速度 | 内容即时生效；壳极少发版 | EAS Update OTA 热更 JS 层 + 商店慢速原生层 | 发版制 | 审核制（1~3 天） |
| 商店过审风险 | 中：iOS 4.2 要求原生价值，靠插件功能证明 | 低 | 低 | 微信审核（类目/支付合规） |
| 与现有栈匹配 | 高（就是现有 Web） | 高（React/TS，monorepo 结构现成） | 低（Dart） | 中（Taro=React 语法） |

## 方案 A：Capacitor 正式化（Web 单代码库三端）

**思路**：把现有 Next.js 拆成「纯静态客户端 + API 服务」，用 Capacitor 打 Android/iOS 包，原生能力全走插件（本地通知、分享目标、生物识别、文件、Live Update 热更）。

**前置改造（本方案的真实成本所在）**：
1. `apps/web` → 纯客户端（`output: export` 或客户端渲染），SSR 仅服务 Web 可保留双模式
2. 认证：HttpOnly Cookie → Bearer token + 安全存储（原生端 WebView 域与 API 跨域，Cookie 方案不可持续）
3. API 加 CORS；后端逻辑零改动（43 个 route 平移）

**评价**：2~3 周即可三端可售，UI 零重写，是**预算/速度优先的正解**；移动端体验天花板 = Web（冷启动/离线短板依旧，见 docs/13）。可作为向方案 B 演进的台阶——认证与 API 改造在 B 中全部复用。

## 方案 B：Expo + Next.js 双客户端（推荐）⭐

**架构**（monorepo 结构现成，无迁移成本）：

```
apps/web      Next.js（现状不动）
apps/mobile   Expo (React Native + Expo Router)
packages/shared  ⭐新增：API client、类型、业务逻辑（解析规则/农历/复盘缓存逻辑）、设计 tokens
packages/ai / packages/db   不变
apps/web 现有 API routes    加 CORS + token 认证，同时服务三端
```

**体验**：移动端原生级——冷启动 0.1~0.3s、离线缓存、本地通知（补上"提醒"）、流式 ASR、生物识别快登、预测性返回动画；Web 端完全不变。**用户体验综合四方案最佳**。

**迭代速度**：EAS Update 做 JS 层 OTA 热更（延续现在每周多轮的节奏，不伤筋动骨），原生层才走商店发版。

**UI 双写的减负手段**：NativeWind 让 RN 直接写 Tailwind class，现有玻璃拟态设计系统（CSS 变量 + Tailwind v4）可大部分映射到 RN；表单/列表/图表为双实现重点。

**商业化适配最好**：RevenueCat 官方 Expo SDK（订阅/内购/entitlement/流失分析一站式，月流水 $10K 内免费，超出约收 1%）。

**风险**：新功能永远双端 UI（单人开发的真实压力）；iOS 需开发者账号（$99/年）与一台 Mac 出包（EAS Build 云构建可免本地 Mac）。

## 方案 C：Flutter 全端（不推荐）

移动端体验与 B 相当，但 **Web 端是三方案中最弱**（首包重、canvas 文本渲染对中文与无障碍不友好），等于放弃已上线的 Next.js 生产资产重新起步；团队从 TS 切 Dart，`packages/*` 全部无法共享。仅当「移动优先、Web 只是展示页」时才成立——与本产品形态不符。

## 方案 D：微信小程序（补充渠道，非主体）

**价值**：免安装触达微信 13 亿用户、微信登录/分享/支付闭环、录音 API（`wx.getRecorderManager`）齐全，ASR 上传链路可行；Taro 用 React 语法写，与现有栈亲和。

**硬约束**：iOS 端小程序**虚拟商品支付受限**——订阅制产品在 iOS 微信内收不了钱，需引导网页支付；审核与包体积限制。

**定位**：获客与轻量使用入口（"给好友看人际关系图谱"这类分享场景有传播性），不承担主体体验。

## 商业化：渠道抽成与基础设施

| 收款渠道 | 抽成 | 说明 |
|---|---|---|
| Web 直收（微信支付/支付宝） | ≈0.6% 手续费，无平台抽成 | 利润率最高，无审核；已有 .cn 域名与备案基础 |
| Apple App Store | 30%（小企业计划 ≤$100 万/年 → 15%）；**中国区 2026 年起下调至 25%** | 数字服务必须走 IAP |
| Google Play | 30%（15% 档同上） | 海外安卓 |
| 国内安卓商店（华为/小米/OV） | 应用类约 30%（游戏联运惯例 50%） | 上架需软著 + 各渠道单独审核 |
| 微信小程序 | 微信支付 ≈0.6%；iOS 虚拟商品受限 | 见方案 D |

**订阅基础设施**：RevenueCat（跨 Apple/Google/Web 统一订阅管理、entitlement、分析；月流水 $10K 内免费）；国内可自研对接微信支付/支付宝（产品已有完整的用户/账务体系，改造成本可控）。

**变现模型建议**（结合产品现状）：**免费额度 + Pro 订阅**——`token usage` API 已在计量 AI 成本，天然支持"每月 X 次语音速记/复盘免费，超出订阅"；Web 端直收（0 抽成）+ App 内 IAP 双轨并行，用 entitlement 打通权益。

## 推荐路线（分阶段）

1. **Phase 1（现在，0 成本）**：安卓壳已可用；补启动骨架页与本地通知（docs/13 清单）
2. **Phase 2（2~3 周）**：**方案 A 的改造部分先行**——API 加 CORS + token 认证、客户端 API 化。这一步无论最终选 A 还是 B 都必须做，且做完后 A 即可交付三端兜底
3. **Phase 3（4~8 周）**：**方案 B 落地**——`packages/shared` 抽共享层，Expo 移动端开发，追求最佳移动体验
4. **Phase 4（随 Phase 3）**：商业化闭环——RevenueCat + Web 直收双轨，免费额度模型
5. **按需**：方案 D 小程序作为获客实验

**为什么不直接全上 C**：Web 是已验证的生产资产和最低成本收款渠道；任何放弃或降级 Web 端的方案都与现状资产冲突。A→B 的渐进路线让每一步都可交付、可回退。
