# 13 · WebView 壳 vs 安卓原生方案对比（体验 / 交互 / 成本）

> 背景：`feat/android-apk` 分支已交付 WebView 壳（34KB，六大兼容点全实现）。本文回答：**它和真正原生 App 的体验差距到底在哪、值不值得重写、什么时候该增强**。

## TL;DR

- 与原生的**可感知差距集中在 4 点**：冷启动速度、离线可用、系统级通知提醒、商店过审。其余差异（滚动流畅度、手势跟手、键盘处理）在 2026 年的现代 WebView + 本 App 的数据规模下，普通用户几乎无感。
- 原生的真实代价不是"写一遍"，而是**永远维护两套 UI**：当前 35+ 轮迭代、每周多轮发版的节奏下，双端同步是不现实的持续成本。
- 本 App 是**语音输入为主、纯线上数据**的工具，恰好避开了 WebView 的多数短板（无 WebGL、无重动效、无长列表虚拟化压力）。
- 建议路径：**壳保底 + 触发点驱动的渐进增强**（详见文末），不做全盘重写。

## 一、体验与交互差异总表

| 维度 | WebView 壳（现状） | 原生（Compose） | 对本 App 的实际影响 |
|---|---|---|---|
| 冷启动 | 进程 → WebView 初始化 → 网络取 SSR 页 → JS 水合 → 数据请求；4G 下首屏约 1~3s，期间只有深色底 | 本地 UI 先渲染（约 0.1~0.3s 出骨架），数据后到 | ⭐⭐⭐ 每天多次打开速记的场景，启动等待是"不像原生 App"的最直接来源 |
| 离线能力 | 完全不可用（已有断网重试浮层） | Room 本地缓存 + 离线先写后同步 | ⭐⭐⭐ 地铁/电梯里记不了账；原生还能"先录后传" |
| 系统通知 | 无。提醒只是**打开 App 才看到的横幅**（`reminders.tsx`：生日/纪念日/逾期待办） | 本地通知：生日当天 9 点推、待办到期推 | ⭐⭐⭐ "提醒"功能目前名存实亡，这是原生才能解锁的真实价值 |
| 应用更新 | 内容**服务端即时生效**，壳本身几乎不用发版 | 每次改动 = 构建 + 分发 + 用户手动更新（侧载分发尤其痛苦） | ⭐⭐⭐ 壳的**决定性优势**，反向碾压 |
| 返回手势 | `onBackPressed` 已处理，但 Android 13+ **预测性返回动画**（预览要回到哪）在 WebView 中缺失 | 完整支持 | ⭐ 手势导航用户能感觉到一点"不跟手" |
| 下拉刷新 | 无（未实现） | SwipeRefresh 系统级跟手 | ⭐ 低频 |
| 长列表滚动 | React 渲染 DOM，节点多了掉帧（移动端已主动关 `backdrop-filter` 换性能） | RecyclerView/Compose LazyColumn 回收复用，恒定 60/120fps | ⭐ 当前个人数据量无感；动态 feed、年视图积累几年后可能显现 |
| 触控延迟 | WebView 多约 10~50ms，星图拖拽的 DOM 命中测试开销大 | 原生恒定低延迟 | ⭐ 普通用户无感 |
| 键盘/输入法 | WebView 软键盘顶起视口在部分机型有 quirk；密码管理器 autofill 弱 | 系统 IME 完整处理，autofill 完整 | ⭐ 本 App 语音为主，影响小；验证清单需覆盖 |
| 文件/分享 | CSV 导入需 App 内主动选文件（已实现） | 可注册为**分享目标**：微信/支付宝导出账单直接分享进 App | ⭐⭐ 有价值的增强点，非高频 |
| 生物识别快登 | 无 | BiometricPrompt 指纹解锁 + 加密存储 | ⭐ 增强 |
| 大屏/折叠屏 | 拉伸的网页 | 多窗口、大屏双栏布局、Material You 动态取色 | 目标用户以手机为主，暂无影响 |
| 商店过审 | Google Play「最低功能性/垃圾应用」政策明确**拒绝纯网站包装**；国内商店同类风险 | 无此问题 | 仅在上架时成立；**侧载分发无影响** |

（⭐⭐⭐=用户可明显感知，⭐=几乎无感）

## 二、逐功能对照（本 App 的具体页面）

| 功能 | 壳内现状 | 原生能做到的增量 |
|---|---|---|
| 语音记账 | 已达标：授权 → 录音 → 前端转 WAV → 上传 ASR → 文本回填 | 流式 ASR 边说边出字、VAD 自动断句、实时波形、录音中锁屏不断（壳里锁屏即断） |
| 提醒横幅 | 打开 App 才看到 | 真正的本地通知推送（无需服务端改造） |
| 日历四视图 | SSR 分页 + 触控滑动，流畅 | ViewPager 级跟手切换 + 预加载 |
| 人际星图拖拽 | Pointer events 可用 | Canvas 渲染，节点数大也不掉帧 |
| CSV 账单导入 | 系统选择器（已打通） | 分享直达 + 自动识别下载目录里的最新账单 |
| 数据导出 | DownloadManager 下载（已打通） | 分享导出文件到微信/云盘 |
| 双主题 | 网页级切换，localStorage 记忆 | 跟随系统深色模式 + 壁纸取色 |
| 登录 | Cookie 会话保持 | 指纹快登、token 加密存储 |

## 三、路线成本对比

| 路线 | 一次性成本 | 持续成本 | 备注 |
|---|---|---|---|
| **维持壳（现状）** | 0 | ≈0 | BASE_URL 变更才需发版 |
| 壳 + 渐进增强 | 低~中（每个增强 1~5 天） | 低 | 在现有壳上加：启动骨架页、本地通知模块（JS bridge + WorkManager）、页面缓存离线先显 |
| **RN/Expo 重写** | 高（4~8 周） | **高：永久双端** | 只能复用 React *知识*，复用不了代码——Next.js SSR 要重构成纯客户端 + token 认证（后端也要动），UI 全部重做 |
| Compose 全原生 | 最高 | 最高 | 10 页面 + 22 组件 + 43 API 客户端全部重写 |
| Flutter | 同全原生 | 最高 | 额外引入 Dart 生态，团队无积累 |

关键认知：**RN"复用 60% 代码"对本项目不成立**。能复用的只有类型定义和部分纯逻辑（日期/农历规则），因为现有代码绑死了 Next.js 服务端渲染 + Cookie 认证 + Tailwind CSS。

## 四、结论与建议

**现在：壳够用，不重写。** 用户能感知的差距 80% 集中在冷启动，这一项可以低成本优化（见下）。

**渐进增强清单（按性价比排序）：**

1. **启动骨架页**（约 1 天）：壳内先显示品牌色骨架（图标+加载条），WebView 首帧就绪后淡出——直接消除"黑屏等待感"，是体验提升最大的一项
2. **页面缓存离线先显**（约 1~2 天）：WebView 开 HTTP 缓存 / 给网页加 Service Worker（PWA 化），重启 App 先显示上次内容再刷新——冷启动从"网络决定"变"本地决定"
3. **本地通知提醒**（约 2~3 天）：原生 WorkManager 每日拉一次生日/待办，9 点本地推送——补上"提醒"这个名存实亡的功能，也是上架 Play 时"原生价值"的证明
4. **注册分享目标**（约 1 天）：CSV 账单从微信导出后直接分享进 App

**触发重写评估的三个信号：** ①离线速记成刚需（地铁使用占比高）；②要上应用商店且增强后仍被拒；③数据规模让年视图/动态 feed 明显卡顿。在那之前，壳 + 增强的总成本不到重写的 10%。
